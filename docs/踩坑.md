# 踩坑记录

## 为什么手写 asyncio 编排，没用 LangGraph / CrewAI

这个项目的多 agent 编排（正反 worker 并行取证、独立裁决、每条 keypoint 一条独立链路、仓库间全并发）是手写的 asyncio，没套编排框架。不是不会用，是这个场景用框架会丢掉核心的成本优化，具体是前缀缓存这一块对不上。

**前缀缓存的前提是逐字节相同的前缀。** DeepSeek 按「模型 + 前缀」分池，同一段前缀第二次往后发直接命中、几乎不计费。这个项目省钱的主线全压在这上面：同一仓库的 gate、explorer、辩论正反方共享逐字节相同的资料页 system（README 那几千字全流程只算一次），多轮循环只往消息末尾追加、绝不改写历史，工具 schema 和各类提醒都写死成常量保证字节一致，辩论扇出前还先串行跑第一条把拆解那段新前缀焐进缓存再并发。实测完整 top10 检索命中率约 60%、单次成本降约 70%，靠的就是把前缀控制到字节级。

**框架的问题不是「不能缓存」，是它的默认消息编排让前缀很难逐字节对齐。** 前缀缓存是服务端自动做的，跟用不用框架无关，只要发出去的 messages 前缀一致就命中。但 LangGraph、CrewAI 这类框架为了做状态管理和节点编排，会在消息序列里插入节点元数据、每个 agent 维护各自独立的 message 历史、状态在节点间传递时重新拼装——这些都会让本该共享的前缀对不上。想在框架里强行保证「多个 agent 发出的请求共享逐字节相同的前缀」，等于要绕过框架的消息管理自己接管，那框架就没剩多少价值了。

**还有几处针对性设计也是框架给不了的**，都是为「无人值守批量跑几十个仓库」这个具体场景手写的：两级信号量并发闸（全局在飞请求 + 单仓 worker，用 contextvar 下传）、锚点审计打回后的独立修复额度、长链路探查的上下文滚动清理、重复调用死循环熔断。框架给的是通用编排能力，给不了这些贴着场景的兜底。

**结论**：手写 asyncio 换来对消息序列的字节级控制，前缀缓存那 70% 的成本节约才立得住。框架适合控制流复杂、不在意这种极致缓存优化的场景；这个项目的取舍是拿掉框架、保住缓存。
