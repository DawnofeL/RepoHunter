# 踩坑记录

# RepoHunter 踩坑

## 1. 意图理解：Query Understanding 与 Keypoint Understanding

意图理解分两步接力。QU 做减法，把它原来乱猜的活全砍掉，只留「从自然语言里抽搜索词」一件；KU 做加法，把 QU 砍完留下的、用户手写的模糊 keypoint 补成一句有边界的判定标准。QU 砍出来的新问题，正是 KU 要接的。

### i. 踩坑：QU 想一口气吐六样，全崩

QU 最早一口气要吐六样东西：搜索查询 queries、一般 keypoint、优先 keypoint priority_keypoints、目标领域 target_domain、目标项目类型 target_type、语言 languages。当时想着把用户意图拆得越细，后面筛选打分就越有据可依。实际跑下来问题成片，集中在三处。

**keypoint 硬分优先级，把本就稀疏的判定点摊得更薄。** 用户需求本来就模糊，能拆出来的可判断关键点没几个，再人为分成「一般」和「优先」两摞，各自就更稀。真实例子：用户说「找 agent 项目，适合写简历的中小型，要有多 agent」，优先要求写「一定要多 agent」。QU 把 multi-agent 这个最核心的概念正确地归进了 priority_keypoints，结果一般 keypoint 只剩一条 small to medium scale。整个需求最关键的词，反而不在主 keypoint 里。

**这把后面的打分直接炸了。** content filter 的 normal_score 是 hit 数除以 (hit + miss)，过线 60。keypoint 只有两条时，可能的得分只有 0、50、100 三档，一条 miss 就从 100 直接掉到 50，过不了线。60 分的门槛压在两条 keypoint 上等于一道悬崖，命中率没有平滑过渡的空间，多踩一条就出局。需求越模糊、keypoint 越少，这道悬崖越陡，筛选结果完全由一两条判定的偶然性决定。

**领域、类型、语言靠 LLM 从自然语言抽，不准也不可控。** 语言尤其明显，用户说「Python 的」抽得出，但表达稍微绕一点、或者根本没提，QU 就只能填 null 或瞎猜。领域和类型同理，全凭 LLM 对一句模糊话的理解，时好时坏，没法复现。这三样其实用户心里都清楚，能直接从下拉框选，不需要 LLM 猜。

### ii. QU 收敛：只抽搜索词，其余交还用户和排序

三个坑指向同一个方向，把 QU 不该管的都摘掉。

- **keypoint 不再分优先级。** 一个需求要么是 keypoint 要么不是，不再分两摞。
- **领域、类型、语言改成前端字段，用户自己填。** 语言走检索硬过滤，搜索时直接拼 language: 限定，在深挖之前就把语言不符的仓库挡在外面；领域和类型也交给用户在前端选，不再让 LLM 从一句话里猜。
- **取消打分和过线，改成命中数排序。** 承接上面那道 60 分悬崖，根因是把稀疏的命中硬算成百分比再卡一条线，少量 keypoint 下百分比跳变本就剧烈，再设一条 pass 线等于让偶然性决定生死。新设计不算分、不设 pass/fail，每个仓库只展示一个像 3/4 这样的「命中数 / 总数」，miss 和 unknown 都算没命中、不区分（LLM 判 miss 还是 unknown 本就常错，对用户来说判错和没看清都不是 hit，索性只数对的）。排序按命中数降序，平手比 stars，被 gate 跳过的和降级的沉底。深挖阶段不再淘汰仓库，所有进来的都排序展示，够不够由用户看命中数自己判，不交给一条武断的阈值。

QU 从此只干一件事：从自然语言抽 queries，keypoint 原样带回不改写。输出从六样缩到两样，压力小了，可控性反而上来。

### iii. QU 的 skill 巧思

QU 只剩抽搜索词一件事，skill 把这件事的坑一条条钉死，都是为了让抽出来的 query 在 GitHub 上真能搜到东西。

- **严禁瞎编，最高优先级铁律。** 只对用户真说出的概念扩同义词、单复数、拼写变体，不许扩成用户没提的别的概念。用户说 agentic，扩成 agent 可以（同一概念的不同写法），扩成 multi-agent 不行，那是用户没提的另一个概念。反例：用户要「目标检测、YOLO」，若扩成 `(object-detection OR detection OR OCR OR image-captioning OR YOLO)` 就错了，OCR 是文字识别、image-captioning 是图像描述，两个用户没提的别的视觉任务被硬塞了进来；正确的只到 `(object-detection OR detection OR YOLO OR You Only Look Once)`，YOLO 是简写就补个全称，别的任务一个不加。
- **query 只放项目的核心身份概念，用户的功能要求一律不进。** GitHub 仓库搜索里空格分隔的概念组是 AND 关系，每多一组就把召回窄一截。用户要「agentic RAG，带 reranker、bm25、dense vector、evaluation」，把这些要求全塞进搜索看着合理，可真写成 `(agentic OR agent) (RAG OR ...) (reranker OR rerank) BM25 (dense vector OR ...) (evaluation OR ...)`，就等于要求一个仓库的名字、描述、topics、README 里同时出现这六样，现实几乎没有，直接搜出 0 个。正确的只搜身份概念 `(agentic OR agent) (RAG OR retrieval-augmented-generation)`，reranker、bm25 这些功能要求留给后面深挖阶段逐条判，不进 query。
- **OR 项不加引号，带空格的写法也直接写。** 「多智能体」写成 `(multi-agent OR multi agent OR multiagent)`，不能写成 `"multi agent"`。引号短语和别的项 OR 在一起，GitHub 会静默返回 0 个。
- **多语言概念先抓全再翻英文。** 「多agent」里「多」是中文的 multi、「agent」是英文，得合成 multi-agent，不能因为「多」是中文就只抓 agent。先把各种语言表达的概念识别全，再统一翻成英文，因为 GitHub 上仓库名和描述几乎全是英文。

### iv. 踩坑：keypoint 太糙，同一条在不同仓库被判出不同标准

QU 收敛后，keypoint 原样交给下游逐条判。但 keypoint 是用户手写的大白话，模糊、没边界，一放到多个仓库横向比就出问题。一次真实搜索（keypoints 为 LLM rl、text LLM only、有提供训练数据、不要几百mb大项目，20 个候选仓库）里，「有提供训练数据」这一条：

- databrickslabs/dolly：代码从 HuggingFace 加载外部数据集 dolly-15k，仓库内无数据文件，判 hit。
- huggingface/trl：提供数据集加载脚本，需外部下载，判 miss。
- HKUDS/GraphEdit：提供下载链接和构造脚本，判 miss。
- build-your-own-x：教程里随机生成 XOR 合成数据，判 hit。

dolly 和 trl 的情形本质相同，判定却相反。根因不在辩论内部：每个仓库的裁决是一次独立调用，互相看不见，「提供」到底指仓库内含文件、还是指明数据来源，这个模糊词的操作化定义在每场辩论里被现场重新发明一次。单场内部都自洽，横向放一起就不一致，而排序恰恰是横向比命中数，命中数因此失真。

先考虑过在裁决全部完成后加一次「横向一致性复核」调用，把所有仓库对同一 keypoint 的判定拼表纠偏。否掉：这是下游补丁，每次搜索都要花一次常备成本，且复核方没读过代码，证据摘要里可能缺按新标准判定所需的信息，还得配一套防它自己出错的边界规则。问题出在上游，就该在上游修。

### v. KU：进流水线前，把每条 keypoint 编译成统一标准

上游修法就是在 QU 之后、与检索并行加一步 Keypoint Understanding。对每条用户手写的 keypoint 各发一次独立调用（全部并发，单条只吐一句话、不用输出 JSON，某条失败给空串也不挡别条），编译出一句操作化的判定标准：

```
原文: 有提供训练数据
标准: 仓库内含现成数据文件，或代码含指明具体数据集、可直接运行的加载管线。仅给下载链接或需自行构造的不算
```

标准注入 gate 和辩论三方（正方、反方、裁决）的 keypoints 占位，所有仓库的所有 agent 拿同一把尺子，漂移在源头消灭。附带收益：取证方有了方向，知道去查「仓库内有没有数据文件」这件具体的事，而不是自己琢磨「提供」是什么意思。

几条边界，都是 skill 和实现里钉死的：

- **原文永远保留，标准是附加字段，不是重写替换。** scoring 的 `_align` 按原文精确对齐，前端展示用原文，标准只进 prompt。实现成替换会直接弄崩对齐。
- **数字条（体积、star 数）同样编译成标准给 LLM 判，不走代码直判。** 「几百mb」这种模糊阈值让 LLM 拿着标准对系统给的体积数字现场掂量，比硬编码一个阈值稳；判定路径全走辩论，一条链路没有分叉。标准写成「体积几百 MB 以下算，明显超过不算，看实际体积掂量」，不写死精确数。
- **编译 skill 顶格写死铁律：只把用户说出的概念操作化，严禁引入原文推不出的条件。** 用户说「有提供训练数据」，可以把「提供」说清楚，严禁私自补「且数据量超过一万条」「且高质量标注」这些用户没提的。与 QU 的严禁瞎编同源。
- **编译失败降级为无标准直通。** 等于回到没有这个模块的行为，流水线不阻塞，只打警告。
- **前端在意图理解阶段回显每条标准。** 搜「text LLM only」时 trl 因内置多模态支持被判 miss，判定本身忠实字面，但用户的意图可能是「排除视觉方向的项目」而非「功能集不含多模态」。标准亮出来，理解偏了用户当场改，系统不猜意图。

QU 把 LLM 乱猜的都拿掉、只留抽词，KU 给留下来的 keypoint 补上它缺的那层边界。一个减一个补，共同保证进入深挖的是「能搜到的候选」加「能一致判定的尺子」。

## 2. Content Filter 模块

### i. 设计决策：tool-use loop 而不是 ReAct

Content Filter 的探查引擎常被叫成「ReAct agent」，但实现上是纯 tool-use loop，两者有本质区别，这里说清楚为什么选后者。

ReAct（论文原意）要求模型在回复里显式写出 `Thought: ... Action: ... Observation: ...` 标签，思考过程出现在输出 token 里。tool-use loop 不要求这个，模型直接调工具，推理在前向传播里隐式完成。

代码里的循环结构（[engine.py](../hunter/content_filter/engine.py)）是这样：

```
while True:
    if 工具用满: 追加逼停消息，强制 json_object 收尾
    resp = _call_explore(messages)   # 带工具，auto
    if not msg.tool_calls: break     # 没调工具 → 这轮就是最终 JSON
    messages.append(assistant_dict)  # 存进历史
    outs = gather(_run_tool...)      # 并发跑工具
    messages += results_msgs         # 结果追加进历史
```

停止判据只看有没有 `tool_calls`，不信 API 的 `stop_reason`（CC 源码 query.ts:554 明说不可靠，实测一致）。

**选隐式 tool-use loop 而不选显式 ReAct 的原因：**

现代 LLM（DeepSeek、Claude 这类）在预训练和 RLHF 阶段已经把 tool-use 推理内化，模型决定调哪个工具、下一步怎么走的推理发生在前向传播里，不需要显式写 Thought 出来才能推得好。强制 Thought 标签是用 prompting 弥补老模型能力的手段，对现代模型是额外噪声。

隐式的具体好处：

- 省输出 token。Thought 文字全是输出，收费且拖慢延迟。隐式推理零输出成本。
- 前缀缓存命中率高。显式 Thought 内容每轮都不一样，会污染 assistant 消息让下一轮前缀 miss。tool-use loop 的历史只有工具调用和结果，结构稳定，缓存命中稳定。
- DeepSeek 有内置 thinking token，推理在隐藏层里已经发生，再加显式 Thought 等于双重推理。

显式 ReAct 唯一占优的场景是任务规划复杂、需要多步推理才能决定下一个 action。探查 repo 判 keypoint 的每步决策相对独立，用不上。

### ii. 踩坑：逼停收尾的 JSON 被模型用大白话糊掉，一个仓库十几万 token 全损

工具预算用满会追加一条逼停消息、强制 `json_object`，逼模型交出最终拆解。但模型偶尔彻底不听格式指令，把拆解内容整段用大白话吐出来，直接解析就崩。一个仓库探查下来十几万 token 全压在这最后一步，栽在格式上等于整份白算，太亏。

`_parse_final` 收尾走三级，一级不行落下一级：

- 直接解析这次的输出。
- 不行就只让模型修格式重试一次：把它刚吐的原样回灌，附一句「照契约把它修成合法 JSON」。
- 还不行最后抢救一次：把上一步的输出当素材，让模型照输出契约把里面的内容硬提成 JSON。

三级都失败才返回 None。多花的这两次调用几乎不额外烧钱：重试和抢救都接在原历史后面、前缀一个字节没变，直接命中缓存。救的是一个已经花掉十几万 token 的仓库，多问一两次能救一个是一个。

### iii. 踩坑：多轮探查把读到的源码堆进历史，二十轮撑爆上下文

探查是带工具的多轮循环，每轮读到的文件正文原样追加进历史，读得越多历史越长，二十轮下来很容易把上下文撑爆。

`_rolling_clean` 每轮末尾清一道，纯代码不调模型。先量 system 之外积了多少 token，没到触发线（20K）什么都不做；到线了走阶梯降级：先留最近 5 个读文件返回、把更早的正文换成占位符，量一下剩余够不够目标（12K），够就停；不够就少留一个再清再量，一路减到只剩最近 1 个。留 1 个还超，说明这最后一段自己就太大，按「4 字符约 1 token」把超出的量折回字符数、从尾部截断到刚好压进目标。清掉的段带上「原来是哪个文件哪几行」，模型日后要回看能精准重定位。

一条边界钉死：清理只保命、绝不叫停探查。探查何时停只由工具预算和死循环熔断决定，清理跟它彻底解耦，无论压掉多少都不影响循环继续。

### iv. 缓存焐热：辩论扇出前先串行跑第一条

拆解拼在 system 尾部，一条 keypoint 的分诊、正方、反方、裁决都共享这段前缀。如果所有 keypoint 一上来就全并发，它们会同时抢着写这段还没建好的新前缀，谁都命中不了缓存，等于同一段拆解被当 miss 重算 n 遍。

`explore_one` 扇出时先串行跑第一条 keypoint，把这段拆解前缀焐进缓存，再 `asyncio.gather` 并发其余，后发的这些大概率命中已焐热的前缀。这是把「省钱靠字节级前缀缓存」贯彻到扇出时序上的一个精细动作，跟同一仓库 gate、explorer、辩论各方共享资料页 system 是同一条主线。

## 3. 模型选型与缓存

### i. 踩坑：想给 coarse 和 content 分别用 flash 和 pro，但缓存不跨模型命中

最早的想法是省钱，coarse 只看全名 description topics readme 目录树，判断简单，用便宜的 flash 就够；content 要Content Filter源码逐条判 keypoint，难一点，上 pro。两个阶段各用各的模型，按难度配算力。

实测发现这条路走不通。拿同一段 system 前缀先喂 flash 焐热缓存，再喂 pro，pro 的命中 token 是 0，命中率 0%。**deepseek 的前缀缓存按模型各管各的，flash 焐热的缓存 pro 用不上，反过来也一样。**

这一拆反而更贵。coarse 用 flash 把那份 system 加 readme 加目录树焐进 flash 的缓存，content 换成 pro 又得把同样的前缀重新当 miss 算一遍输入 token，等于同一份前缀付了两遍钱。

所以干脆把两阶段合并进 repo detection，coarse 和 content 都用 pro，共享同一份 system prompt。Content Filter 第一轮直接命中 coarse 焐进缓存的 readme 和目录树，输入 token 大部分走命中价，整体反而比 flash 加 pro 分开更经济。验证缓存命中的两个函数见 [Repo_Analyzer.ipynb](../Repo_Analyzer.ipynb) 末尾的 `ds_flash` 和 `ds_pro`。








## 为什么手写 asyncio 编排，没用 LangGraph / CrewAI

这个项目的多 agent 编排（正反 worker 并行取证、独立裁决、每条 keypoint 一条独立链路、仓库间全并发）是手写的 asyncio，没套编排框架。不是不会用，是这个场景用框架会丢掉核心的成本优化，具体是前缀缓存这一块对不上。

**前缀缓存的前提是逐字节相同的前缀。** DeepSeek 按「模型 + 前缀」分池，同一段前缀第二次往后发直接命中、几乎不计费。这个项目省钱的主线全压在这上面：同一仓库的 gate、explorer、辩论正反方共享逐字节相同的资料页 system（README 那几千字全流程只算一次），多轮循环只往消息末尾追加、绝不改写历史，工具 schema 和各类提醒都写死成常量保证字节一致，辩论扇出前还先串行跑第一条把拆解那段新前缀焐进缓存再并发。实测完整 top10 检索命中率约 60%、单次成本降约 70%，靠的就是把前缀控制到字节级。

**框架的问题不是「不能缓存」，是它的默认消息编排让前缀很难逐字节对齐。** 前缀缓存是服务端自动做的，跟用不用框架无关，只要发出去的 messages 前缀一致就命中。但 LangGraph、CrewAI 这类框架为了做状态管理和节点编排，会在消息序列里插入节点元数据、每个 agent 维护各自独立的 message 历史、状态在节点间传递时重新拼装——这些都会让本该共享的前缀对不上。想在框架里强行保证「多个 agent 发出的请求共享逐字节相同的前缀」，等于要绕过框架的消息管理自己接管，那框架就没剩多少价值了。

**还有几处针对性设计也是框架给不了的**，都是为「无人值守批量跑几十个仓库」这个具体场景手写的：两级信号量并发闸（全局在飞请求 + 单仓 worker，用 contextvar 下传）、锚点审计打回后的独立修复额度、长链路探查的上下文滚动清理、重复调用死循环熔断。框架给的是通用编排能力，给不了这些贴着场景的兜底。

**结论**：手写 asyncio 换来对消息序列的字节级控制，前缀缓存那 70% 的成本节约才立得住。框架适合控制流复杂、不在意这种极致缓存优化的场景；这个项目的取舍是拿掉框架、保住缓存。
