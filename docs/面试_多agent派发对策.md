# 面试对策：多 agent 探查怎么派发任务（以 DeerFlow 为例）

## 0. 一句话

主 agent 花极少的工具预算浅探仓库骨架，按真实的架构边界把仓库切成几个探查区，一个区派一个子 agent 并行深挖，最后一个收尾调用把各区结果合并。切几个、谁先谁后，由主 agent 看这个具体仓库的结构当场决定。

## 1. 主 agent 到底读什么、读多深来分区

这是被追问最狠的地方，粒度必须说死。

**起手免费拿到的两样（零工具调用）**

资料页里已经塞好了 README 和两层目录结构树。主 agent 先把这两样读干净，这一步不花工具次数。多数分区判断，看这两层树加 README 就够了。

**工具预算只有 5 次，只花在消歧上**

主 agent 带四个只读工具（列目录、读文件、grep、按名找文件），预算封死 5 次。这 5 次的唯一用途是把两层树里看不清的边界确认清楚，严禁拿它替子 agent 深挖。典型花法：

- 某个顶层目录文件特别多，两层树看不出它是一个模块还是好几个，就对它列第三层目录，看要不要拆成多个区。
- 仓库根有框架配置文件（如 `langgraph.json`、`pyproject.toml`），读一眼确认技术栈和编排入口在哪个目录，编排区就锚定在那。
- 读一个入口文件的头部，确认子 agent 从哪里被派生、核心对象在哪装配。

**读到什么深度**

默认就是资料页给的两层。只对少数几个「大到可能内含多个模块」的顶层目录，用工具钻到第三层，其余目录停在两层。判断要不要钻第三层的信号，就是这个目录下的文件数和子目录数，多且杂的才钻。

**分区依据的三类具体信号**

- 目录名自带架构语义。`agents`、`runtime`、`tools`、`sandbox`、`memory`、`skills` 这种名字本身就是一个架构模块，直接成候选区。
- 密度。一个目录文件多、子目录多，说明它是块厚料，值得单独一个区。一个目录只有一两个文件，归并进邻近区或直接不设区。
- 框架信号。配置文件和依赖清单点明这是什么框架，编排逻辑就落在框架约定的那个位置，编排区据此锚定。

## 2. DeerFlow 实例：分了哪几个区

DeerFlow 核心运行时在 `backend/packages/harness/deerflow/`。主 agent 读两层树看到的顶层模块和它们的分量（文件数）：agents 75、runtime 35、skills 30、tools 16、sandbox 15、subagents 10、memory（在 agents 下）。据此它花 5 次工具里的一两次，对 `agents/`（75 个文件太厚）列第三层，看到里面 `lead_agent/`、`middlewares/`、`memory/` 是三块独立的料，于是把 agents 拆开。最终切出 6 个区（命中上限，正合一个大项目）：

| 区 | 负责路径 | 探查焦点 | 分它出来的信号 |
|---|---|---|---|
| 编排核心（串行先跑） | `agents/lead_agent/`、`subagents/`、`agents/factory.py`、`agents/goal_state.py` | 主 agent 怎么拆解目标、怎么派生和管理子 agent、目标状态怎么在两级之间流转 | 名字即编排语义，是理解全局的钥匙 |
| 中间件管线 | `agents/middlewares/` | agent 的各种行为（上下文压缩、循环检测、token 预算、技能激活、工具策略、子 agent 上限）怎么用一层层可插拔中间件叠出来 | 一个目录就 40 个文件，行为主要载体 |
| 运行时底座 | `runtime/` | LangGraph 之上的运行时，状态检查点、事件流、run 生命周期、上下文压紧怎么落地 | 35 个文件，独立的执行底座 |
| 技能与工具 | `skills/`、`tools/` | 技能怎么按需渐进加载、内置工具怎么定义和路由 | 两个名字直白的中等模块，功能连贯 |
| 沙箱执行 | `sandbox/`、`community/aio_sandbox/`、`community/boxlite/` | 代码和命令怎么在隔离环境里跑 | 隔离执行自成一块 |
| 长期记忆 | `agents/memory/` | 跨会话记忆怎么抽取、存储、更新、消解陈旧 | 内含独立记忆后端，边界清晰 |

**串行先跑的是编排核心区**。理由：其余五个区都要先懂这套两级编排骨架，才看得清自己在整体里怎么被调起来。它先探出一段概述，作为全局背景注入其余五个子 agent。

**故意不设区的**：`frontend/`（前端另一套技术栈，理解运行时架构用不上）、`config/`、`persistence/`、`authz/`、`tracing/`、`tui/`、`tests/`、`docs/`。这些要么是横切支撑，要么跟架构主干无关，主 agent 直接跳过，省下子 agent。

**每个子 agent 具体负责什么**：拿到同一份仓库资料页开头（逐字节相同，并行时命中同一份前缀缓存），加上自己区的路径清单和一句焦点，独立 12 次工具预算、独立上下文。它只在自己路径里深挖，越界只许快速看一眼确认、不深挖。产出自己这个区的局部拆解，每个设计点带真实文件加符号的锚点。

## 3. 派多少个：从信号到数量

区数等于「两层树里，每个需要连续读同一批文件才能弄懂的独立架构模块」的个数，卡在 2 到 6 之间。这个数跟着结构走，体积只当密度参考。

- DeerFlow：agents 拆成编排、中间件、记忆三块，加 runtime、skills 与 tools、sandbox，共 6 个，撞上限。
- TradingAgents：结构聚拢，编排图、agent 角色、数据与工具三块，切 3 个。
- 目录树一眼看全的小仓库：主 agent 判单区，整个仓库一个子 agent，等价退回单 agent。

动态性来自把决策权交给看得见真实结构的主 agent。代码里没有一条「体积大于 X 就派 Y 个」的阈值，主 agent 看几个模块就切几个区。这跟判定标准那套「让模型拿标准现场判、避开硬编阈值」是一条思路。

## 4. 串行并行怎么判、怎么 assign

判据只有一条：**看懂 A 区，要不要先有 B 区的产出。**

- 编排核心区是全局钥匙，其余区要先懂它才看得清全局协作，它标为串行先跑，产出概述当背景喂给其余区。
- 其余各区之间没有这种理解依赖，各看各的路径，全部并行扇出。

所以执行结构是「一个串行前置加其余全并行」。串行只留给真正是全局钥匙的那一个区，其余一律并行。这条判据跟教子 agent 判「多个工具调用能不能同一轮并发」完全一致：要填的参数得等别的结果就先后做，用不着等就一起上。

## 5. 子 agent 的任务边界：软边界，不锁文件系统

**方案**：主 agent 分区给的路径是目录级别的范围，写进子 agent 的任务提示里当约束，工具层不做任何文件系统隔离。子 agent 手上的四个工具能读到克隆目录里的任何文件，边界靠提示词遵守，不是权限拦截。

**规则两条**：

- 深挖只在自己负责的路径内做，产出的设计点也只归本区。
- 代码引用了区外模块、不看一眼理解不了时，允许快速读一小段确认，严禁在区外深挖。

**主 agent 不需要通读全仓库**：

- 分区判断只看目录名和两层目录树的名字信息（README 和两层树是资料页免费给的，零工具调用），不涉及读任何文件正文。
- 分区清单填的是目录路径，不是文件枚举。比如中间件区就是一条 `agents/middlewares/`，不需要把这个目录下几十个文件名都列出来。
- 子 agent 拿到目录路径后，自己在里面用工具进一步探查、决定读哪几个文件，这是子 agent 自己花预算做的事，不是主 agent 替它准备的。

**为什么不做硬边界（工具层禁止读区外文件）**：跨文件引用会直接断掉。角色区的代码 import 编排核心区的类，硬锁下这条路走不通，子 agent 只能瞎猜。软边界留了「跳出去确认」这个口子，硬边界没有。

**软边界的越界风险，四样东西兜住**：

- 串行钥匙区（编排核心）先跑，产出的概述注入其余每个子 agent 当背景，跨区依赖大部分被这一步提前消化掉。
- 子 agent 的产出只认本区，就算瞄了区外几行，也不往外产出区外的结论。
- 汇总阶段统一去重，两个区偶尔报了同一处，合并时留信息全的那份。
- 12 次工具预算封顶，越界乱翻也翻不了几步。

## 6. LangGraph 具体怎么写

DeerFlow 本身就跑在 LangGraph 上。这套编排用它的三个核心概念就能搭起来。下面每个概念先用大白话讲清，再给一句你能当场说出口的话，最后才是代码，你不用背代码，把前两层讲顺就够侃了。

**先建一个心智模型（这段就是你开口的第一句）**

LangGraph 让你把一个复杂流程画成一张流程图。图上每个方框叫一个节点，是一步具体工作。方框之间连线，规定这步走完去哪步。全程有一份共享的状态在图里流动，每个节点读它、把自己的产出写回去，下一个节点接着用。多 agent 编排最难的一点在于「一步要炸成很多步同时并行」，LangGraph 专门有个叫 Send 的机制解决这个。

**概念一：节点加状态，这是图的骨架**

- 大白话：把流程拆成几个方框，一个方框干一件事，一份状态贯穿全程。我这里拆成四个方框，规划、串行探、并行探、汇总。
- 代码里对应：`StateGraph` 建图，状态里开几格，装资料页、克隆目录、分区结果、各区报告、最终拆解。`add_node` 挂一个方框，`add_edge` 把两个方框连起来。
- 你能说的话：「我用 StateGraph 把整个探查拆成规划、串行探查、并行探查、汇总四个节点，一份共享状态在节点之间流转。」

**概念二：Send，一步炸成 N 个并行，这是整套的灵魂**

- 大白话：主 agent 当场切出几个区，我事先不知道是三个还是六个。Send 让我在运行的那一刻，有几个区就现生成几个并行分支，每个分支塞一个区的活，同时开跑。
- 类比：像主管开会时把当天的活当场分成几摞、一摞发一个人同时干，分几摞看当天工作量定，人数不是提前写死的。
- 代码里对应：在一条条件边上返回一串 Send，每个 Send 指向同一个子 agent 节点、但带不同的区。LangGraph 收到几个 Send 就并发跑几个。
- 你能说的话：「并行度是运行时决定的，我用 LangGraph 的 Send 在条件边里按分区数动态扇出，切几个区就并发几个子 agent，这就是它的 map-reduce 写法。」

**概念三：reducer，并行结果怎么不打架地汇回一处**

- 大白话：几个子 agent 同时往状态里同一格「各区报告」写东西，普通写法后写的会盖掉先写的。reducer 就是告诉框架这一格用「累加」来合并，每个子 agent 写的自动追加进一个列表，谁都不丢。等所有分支都写完，框架自动把流程汇到汇总那一步，这道「等所有人到齐再往下」的栅栏它替我管好。
- 代码里对应：状态里那一格标成一个「用相加合并」的类型。
- 你能说的话：「并行分支的结果我用 reducer 归并，标成列表相加，框架自动把每个子 agent 的报告累加进来，并且在全部完成后设栅栏汇合，join 我不用自己写。」

**下面这段代码就是上面四个方框和三个概念的落地，看注释对照着上面读**

```python
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

class State(TypedDict):
    system: str                              # 仓库资料页
    local_root: str                          # 克隆目录
    zones: list                              # 主 agent 分出的区
    serial_context: str                      # 串行区产出的全局背景
    reports: Annotated[list, operator.add]   # 各 worker 累加进来
    dissection: dict                         # 最终拆解

def supervisor_plan(state):
    # 浅探分区，LLM 带 5 次工具预算，返回 zones 和哪个区串行先跑
    zones = plan_zones(state["system"], state["local_root"])
    return {"zones": zones}

def serial_first(state):
    # 先跑标了串行的那个区，产出全局背景
    z = pick_serial(state["zones"])
    rep = explore_zone(z, global_context="")
    return {"serial_context": rep["summary"], "reports": [rep]}

def fan_out(state):
    # 核心：用 Send 动态派发，剩几个区就发几个并行分支
    return [Send("zone_worker",
                 {"zone": z, "serial_context": state["serial_context"],
                  "system": state["system"], "local_root": state["local_root"]})
            for z in parallel_zones(state["zones"])]

def zone_worker(state):
    rep = explore_zone(state["zone"], state["serial_context"])
    return {"reports": [rep]}                 # reducer 自动累加

def merge(state):
    return {"dissection": merge_reports(state["reports"])}

g = StateGraph(State)
g.add_node("supervisor_plan", supervisor_plan)
g.add_node("serial_first", serial_first)
g.add_node("zone_worker", zone_worker)
g.add_node("merge", merge)
g.add_edge(START, "supervisor_plan")
g.add_edge("supervisor_plan", "serial_first")
g.add_conditional_edges("serial_first", fan_out, ["zone_worker"])  # Send 扇出
g.add_edge("zone_worker", "merge")
g.add_edge("merge", END)
app = g.compile()
```

`add_conditional_edges("serial_first", fan_out, ...)` 里 `fan_out` 返回几个 `Send`，LangGraph 就并发跑几个 `zone_worker`，全部落地后自动汇到 `merge`。这就是「运行时决定并行度」的标准写法，官方叫 map-reduce 模式。

**还有个现成的 supervisor 包**

`langgraph-supervisor` 的 `create_supervisor` 也能搭多 agent，走的是一个 supervisor 反复决定「下一步交给哪个 worker」的对话式交接。它更适合流程本身不确定、要来回踢皮球的场景。我这套是「先一次性规划好 N 个区、再并行铺开」，用 `Send` 的 map-reduce 更贴，所以我采用 `Send` 这条。两种都能讲。

**面试要主动挑明的取舍**

`Send` 派发时，LangGraph 会给每个 worker 的状态注入编排元数据，各 worker 又维护各自的消息历史。这会打乱本该逐字节相同的前缀，我的前缀缓存优化就受影响。所以真实实现里，编排我按这个 supervisor-worker 模式手写，复用已有的并发闸、工具循环、成本计量，把每个子 agent 发出去的资料页开头控制到字节一致，缓存才保得住。LangGraph 的 supervisor 模式我讲得清、也在别的项目用过，这里为了缓存选了手写。这一点跟踩坑文档里「为什么不套框架」完全自洽。

## 7. 可能被追问的硬问题

**问：模型分区分错了怎么办？**
三道保底。下限是小仓库判单区、退回单 agent。上限封 6 个区防失控。分区给的每条路径都会核对真实存在、编造的丢弃。最坏整个多 agent 环节失败，自动回退单 agent，结果照出。

**问：并行的子 agent 会重复探同一块吗？**
分区路径互斥，每个子 agent 限定在自己路径深挖，越界只许快速确认。

**问：各区各判各的，合并会前后矛盾吗？**
汇总阶段统一去重、写贯通总览来收口。这一步产出的是对项目的客观描述，跨区不一致的风险比正反辩论那种判断类任务轻。

**问：比单 agent 强在哪，有数据吗？**
强在大仓库覆盖。单 agent 只有 20 次预算和一个上下文，面对 DeerFlow 这种量级铺不开、会漏设计点。多 agent 每区独立预算、独立上下文，覆盖更全、漏得更少。我会诚实说明这是架构性改进，严格量化要另建标注集，我还没做。
