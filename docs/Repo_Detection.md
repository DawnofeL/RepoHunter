## Repo Detection

从用户需求到排序结果的完整流水线，按处理顺序分四个阶段：

- S1 的 QU 把需求重写成查询关键词并检索出候选池。
- S2 的 KU 重新把用户语言扩写为具体的判定标准，gate 根据预抓资料（full name, clean README etc.） 粗筛。
- S3 的 Content Filter 使用四个工具读源码撰写项目结构观拆解。
- S4 逐条 keypoint 辩论裁决后排序。

`content_filter.py` 是把 S2 到 S4 串起来的总编排，`pipeline.py` 再往外套一层、把 S1 也接上。

### S1 QU & Repo Search

用户的需求清单进来，抽出 GitHub 能搜的查询词，语言字段纠错归一后当硬过滤，检索去重出候选仓库池。

按序读三个文件：

1. `pre_filter/query_understanding.py`：调模型从需求清单抽搜索查询，keypoints 原样带回不改写；输出 JSON 坏掉走修格式重试、正则抠取、空壳兜底三级。skill 在 `skills/query_understanding.md`。
2. `pre_filter/repo_languages.py`：语言名三级归一（别名、精确、模糊），两字母以内不走模糊防错纠；Python 和 Jupyter Notebook 绑成一对同搜。
3. `pre_filter/search_repo.py`：每条查询剥引号合成单条 OR 组（带引号短语和 OR 混用 GitHub 会静默返回零结果），拼上语言、归档、fork 限定并发搜，按仓库全名并集去重。

这三步拼出的查询要发给 GitHub，接上 GitHub 这一步由 `clients.py` 管：搜之前先用它接上 GitHub 的搜索服务、拿用户填的 token 做鉴权，把一条能直接发搜索请求的通道交给上面第 3 步用，搜完断开。search_repo 只管拼查询，连上和断开归 clients 管。





### S2 Pre-Filter

深挖前的三样准备：把每条 keypoint 编译成一句可判定的标准，让所有仓库用同一把尺子；预抓 gate 和后续角色要看的资料；gate 只看资料判整体方向，明显不符的软跳过（置灰沉底不淘汰，拿不准一律放行）。

按序读三处：

4. `pre_filter/keypoint_understanding.py`：每条 keypoint 独立并发编译成一句判定标准，单条失败给空串不挡流程。skill 在 `skills/keypoint_understanding.md`。
5. `repo_detection/prefetch.py`：走 GitHub API 预抓三样：README（按标题砍掉 changelog、license 等噪声段再截断）、两层目录树、stars 和体积。体积拼进 system 给模型判体量，防 README 自称轻量误判。
6. `repo_detection/explorer.py` 里的 `_call_gate`：不带工具的一次调用，只看预抓资料判 skip 还是 proceed，解析失败默认放行（错跳不可逆）。skill 在 `skills/skip_gate.md`。





### S3 Content Filter

gate 放行的仓库浅克隆到本地，explorer 拿四个只读工具循环读真源码，产出一份不含任何 keypoint 的客观架构拆解（目的、技术栈、带锚点的关键设计、架构总览）。拆解里每个锚点由代码对克隆核验，对不上先打回让模型重修一次，仍对不上删点兜底。

按序读五个文件，先工具后主循环：

7. `repo_detection/agent_tools.py`：四个只读工具的后端（列目录、读文件带行号和已读缓存、ripgrep 正则搜索、按文件名找文件）加发给模型的工具清单，全部对本地克隆操作。

   

   **i. glob_files 按文件名满仓库捞**

   > **参数**

   - `pattern` 文件名通配，`**/` 表示任意深度的目录下，这条就是「不管埋多深，把叫 requirements.txt 的都给我」
   - `path` 不填搜全库，填了限定在某个子目录

   > **示例**

   ```python
   {"pattern": "**/requirements.txt"}
   ```

   这步还没读任何源码，靠常识猜 Python 项目的依赖清单通常叫 requirements.txt、setup.py、pyproject.toml，直接猜名字去捞，比一层层翻目录快。返回「没有匹配的文件」就当场知道这项目不用那个文件。

   

   **ii. list_tree 列一层目录**

   > **参数**

   - `path` 目录相对路径，空字符串列根目录，只列一层，要往深走就对子目录再调一次

   > **示例**

   ```python
   {"path": "metagpt/roles"}
   ```

   返回列出 architect.py、engineer.py 等十几个角色文件，直接坐实「多 agent」。填 metagpt/roles 是推出来的，上一轮读 roles/__init__.py 看到一堆 `from metagpt.roles.architect import ...`，据此判断有个按角色分文件的 roles 目录，才来列它。

   

   **iii. read_file 读一个文件**

   > **参数**

   - `path` 文件相对路径，抄自上一轮 list_tree 的返回
   - `limit` 只读前多少行，`offset` 指从第几行起，配合读中段

   > **示例**

   ```python
   {"path": "metagpt/roles/role.py", "limit": 80}
   ```

   一开始整读 software_company.py 不带参数，到这条给 role.py 加了 `limit`，是因为目录列表里显示 role.py 有 25KB。大文件先读头 80 行看结构、不整吞，拿已知的文件大小决定读多少。

   

   **iv. grep_code 正则搜代码**

   > **参数**

   - `pattern` ripgrep 正则，`|` 是「或」，把候选名字一次全列上搜
   - `path` 限死在已知的 role.py 里，不满仓库搜
   - `output_mode` 默认只回文件名最省 token，要看具体代码行就改成 content，带行号返回匹配行
   - `context` 让匹配行上下各多显示几行、看清函数体
   - 另有 `glob`（只在某类文件里搜）、`head_limit`（最多回几条命中）、`ignore_case`（大小写不敏感）

   > **示例**

   ```python
   {"pattern": "def _react|def run|def _think|def _act|def _observe", "path": "metagpt/roles/role.py", "output_mode": "content", "context": 5}
   ```

   模型想确认有没有 ReAct 循环、但不确定方法具体叫啥，就把可能的名字用 `|` 全列上一次搜。这步已读过 role.py 头部、知道大概在哪，用 grep 精确取那几行、不重新整读大文件。知道要找什么、只想取一小段就用它。

   

   读文件带一套重读规矩，配合下面第 9 点的滚动清理：同一段读过、内容还在上下文里，再读就挡回一句「已读过」，防模型空转白烧钱；一旦这段被清理归档（正文换成了占位符、不在上下文里了），就放行重读，但最多两次，到上限再读也挡，回一句「已达重读上限」，两次上限是防死循环。

8. `repo_detection/tool_loop.py`：explorer 和辩论共用的循环底件：解析模型输出 JSON 带兜底、执行单个工具调用并兜错、拦截重复读 README 和根目录。

9. `repo_detection/explorer.py`：全篇核心。主循环每轮把工具摆给模型，模型调工具就执行回灌进下一轮，不调了这轮回复就是最终拆解；工具预算二十次用满逼停，半程和停滞各注入一次提醒。

   除预算耗尽外还有一道重复调用熔断：把每次调用规约成「工具名+参数」指纹，同一指纹连撞三次判死循环、下一轮强制交卷，不同参数清零不误伤正常连读不同文件（无人值守批量跑，没有人在旁边打断，这道物理兜底不能少）。

   逼停后收尾 JSON 解析走三级：整段解析、修格式重试、最后一次「按契约提取」抢救，一个仓库探查下来十几万 token 栽在最后格式上全损太亏，多一次调用能救一个算一个。skill 在 `skills/content_filter.md`，共享 system 模板在 `skills/system_header.md`。

   长链路防上下文膨胀：探查是带工具的多轮循环，每轮读到的文件正文原样追加进历史，读得越多这个历史越长，二十轮下来很容易把上下文撑爆。为此每轮末尾加一道滚动清理：先用 tokenizer 量一下历史里（system prompt 之外的部分）积了多少 token，没到触发线（20K）什么都不做；到线了就把较早那些读文件的返回正文换成一句占位符，只留最近几个原样。占位符带上「这段原来是哪个文件哪几行」，方便模型日后要回看时精准重新定位，例：`(此处原为 xxx.py 第 120-380 行的内容，已清理以节省上下文，如需可重新读取，至多两次)`。清理全程纯代码、不调模型，快。

   保留最近 n 个工具返回结果逻辑：先试留最近 5 个、清掉更早的，量一下剩余空间够不够目标（12K），够就停；不够就留 4 个再量、一路减到 1 个，先够的停；减到只剩最近 1 个还超，就把这最后一个正文截断到刚好不超、尾部标已截断可重读。这样清理总能把上下文压回目标以内，清理只保命、绝不叫停探查。清理和上面第 7 点的归档重读规矩配套：清一段就把它在缓存里标成归档，模型才有机会把它重读回来。每次清理还往开发者监控记一笔（这个仓库这轮清了谁、当前几个结果活着几个归档、各重读几次），多个仓库并行探查时按仓库分开看，随时能盯住任意一条循环压了多少、清了多少。

10. `repo_detection/audit.py`：锚点审计与自愈：逐个核对拆解里的文件路径和符号真实存在，坏的拼成重修指令打回，重修后仍坏的删掉；辩论论据的锚点也走同一套核验。重修不吃探查那二十次预算，另给一笔独立的三次修复额度（`_repair_round`）：探查阶段常把预算烧光，审计打回的重修又得带工具重查锚点，没有这笔独立额度重修就只能直接删点。真实轨迹里十个仓库四个因预算耗尽丢了设计点（MetaGPT 一口气删三个），这笔额度就是救这个。修复轮的结果就地再审计、不回主循环顶（回顶会撞上预算耗尽的逼停把重查结果覆盖掉），仍坏才删点。

11. `repo_detection/log_visual.py`：Visual 和 ReAct 两种日志格式化，不影响主线，扫一眼即可。



### S4 Debate & Adjudicate

拆解出来后，每条 keypoint 判它到底命没命中。翻源码的活不交给辩论方，由代码按需去做，辩论方只管判断。每条 keypoint 一条独立链路，走三步：

- **分诊**：一次中立的调用，不站正反任何一方。给它看这个仓库的拆解和这一条 keypoint，它只回答两件事，手上的拆解够不够判这条、不够的话要看哪几个文件或符号。够判就直接进辩论，一行源码都不用读。
- **按需取证**：纯代码的活，不花模型调用。要看哪个文件、哪个符号，全是上一步分诊那次模型调用定下的，写在它吐出的清单里；取证这步只照着清单去本地克隆里把那几段源码抠出来，自己不判断该看什么。抠的是一个符号（某个类或函数）周围的一小段，不是整份文件，所以即便命中一个几千行的大文件也只取那一小块。
- **判决**：正反两方拿到同一份材料（拆解加按需抠出的源码），正方举支持证据、反方举反证各表一次态，一个上下文干净的裁决者收口，判这条 hit 还是 miss。

所有链路整体并发，判定结果按下标对齐回清单，最后按命中数排序。

分诊开出的清单要拿去读文件，不能全信模型，得过几道兜底关卡：

- 清单里每一项指向的文件路径和符号，都先对本地克隆核一遍真实存在，对不上的直接丢（模型偶尔会编路径）。
- 一次最多抠几段、抠出来的总量有字数上限，防止一条需求就把源码整本搬进来。
- 清单被兜底关卡砍光、或者分诊的回复格式坏掉解析不出，都退回「只用拆解判」这条路，不让任何一步卡死整条链。模型说的「够」或「不够」只当参考，代码只认清单里真正兑现了的那几段。

举两条需求对比：

- 需求「必须是多 agent」。拆解的关键设计里已经写明「agents 目录下有 12 个不同角色，由一张图统一编排」，分诊判够，正反方直接就着拆解辩，不读源码。
- 需求「项目自带可下载的数据集」。拆解只讲了架构、没提数据，分诊判不够，开清单要看数据目录。代码把那个目录的内容抠出来，发现只有一个下载脚本、没有真实数据文件，反方据此判 miss。

省钱靠共享缓存。仓库的资料页和拆解挂在所有调用共同的开头，一份只算一次钱；每条需求按需抠的那几段源码只抠一次，给这条需求的正反两方共用。够判的需求连源码都不抠，只花分诊那一次的思考钱。

按序读三个文件：

12. `repo_detection/debate.py`：分诊、正反、裁决三方的 prompt 填充和强制 JSON 请求。skills 在 `triage.md`、`advocate.md`、`skeptic.md`、`adjudicate.md`。
13. `repo_detection/evidence.py`：按分诊清单从本地克隆里抠符号周围的源码，核验、限量后拼成一份按需证据交给正反方。
14. `repo_detection/scoring.py`：判定按位置对齐回发出的清单（不靠模型照抄原文），漏判补 miss；数命中数不算分不设及格线；排序按命中数降序、平手比 stars，跳过和降级的沉底。

### 完整运行逻辑

需求清单和语言过滤进来，Query_Understanding 翻成搜索查询（keypoints 原样带回），Keypoint_Understanding 给每条编一句判定标准，语言归一后拼进硬过滤，Search_Repositories 并发搜出去重候选池。

候选池交给 Repo_Detection，所有仓库并发跑，单仓库内部：prefetch 抓 README、目录树、stars/size 拼成六样资料页 system；gate 只看资料页判方向，跳过的直接出结果沉底；放行的浅克隆到本地，explorer 工具循环读源码出拆解、过锚点审计；然后按 keypoint 扇出，每条先分诊判拆解够不够、不够就由代码按需抠源码，正反两方拿同一份材料立刻单条裁决。全部跑完 scoring 按命中数排序。

省钱主线是 DeepSeek 前缀缓存：同一仓库的 gate、explorer、分诊、正反方这些调用共享逐字节相同的资料页 system，README 那三千多字只真算一次钱；多轮循环只往消息末尾追加、绝不改写历史，每轮前缀都完整命中。

搜索侧记忆已经接活：查记忆命中且存过拆解的仓库跳过 explorer 直接复用，没命中的照常深挖，搜完一次写回两张表。对话侧记忆（拼 system、提取、召回、压缩）也已落地，见下方 Memory 节。

## Memory

记忆板块的完整数据流：两条写入路径喂三个库，对话侧再把存的东西读回来用。

```text
【搜索侧】写 history.db
  用户 query
    └─> pipeline：QU → 检索 → gate → explorer 拆解 → 辩论 → 排序
          │   use_memory 开着时，命中有拆解的仓库就跳过 explorer 直接复用（load_memories）
          └─> save_run 一次写两张表
                ├─ repo_memory：一仓库一行，贵拆解按语言分中英两格各存一份 + seen_runs 搜索时间线
                └─ runs：一次搜索一行，轻量增量（判定/trace/token）只留 full_name 指向 repo_memory

【对话侧】读 history.db + 读写 memory.db
  用户消息 + 手动「+」注入的仓库(wsContext)
    └─> build_segments 拼 system：
          ① 人设(llm_skill)
          ② 通用记忆索引：list_general 取 user/feedback/project 三类，
             每条压成一句摘要 +「N 天前」，正文不进上下文
          ③ 注入仓库：get_memory 取拆解 + list_by_repo 取该仓库聊过的 repo 类事实
          ④ 召回 select_from_manifest（每轮先跑一次小模型）：
               清单 = repo_memory(有拆解·未注入) + 三类通用记忆 + 有笔记的过往会话，每条 name + 一句描述
               跳过门：消息不足 4 字 或 纯应答(「嗯」「好的」) → 不调小模型
               小模型回 {picks, ambiguous}（picks 混着三类，代码按名字分派）：
                 picks·仓库  → 补全量拆解，右栏冒出「召回」芯片转正、往后常驻
                 picks·记忆  → 把正文补进「召回的记忆」段
                 picks·会话笔记 → 把那次对话的摘要补进「召回的会话笔记」段
                 ambiguous   → 补候选清单，助手反问用户是哪个
               每次判断 → dev.record（落监控）
    └─> stream_chat：system + 对话历史 → DeepSeek 流式 → delta 逐字上屏
          ├─ 每轮吐 prompt 事件(分段) → 点头像看提示词+召回判断，分段随会话存库(退出重进还在)
          └─ 聊完 spawn_extraction（后台任务，不阻塞回答、失败不影响对话）
                └─> 提取，写 chat_memories
                      触发：新消息攒够 12 条(6 轮) 或 用户说「记住」
                      读游标 → 只取新消息(增量) → 调模型 → 密钥扫描打码
                      → repo 类校验 full_name 真伪(编的丢) → apply_actions 落库
                      → 落成功才挪游标；单飞 + 补跑，同时只跑一个不撞车
                      产出四类：user/feedback/project(三类通用) + repo(带锚点)
                        三类通用 → 下次任何对话进索引、被召回补正文
                        repo 类  → 跟对应仓库的拆解一起注入
  会话本身 → save_session → chat_sessions（messages 含每轮的提示词分段）

【监控】横切，不碰主流程，开关默认关
  召回判断 + 提取过程 → dev.record → dev_audit.db → 前端 🔬 审计视图（落库，重启仍在）

【三个库】
  data/history.db    repo_memory(拆解按语言分格) + runs(每次搜索)
  data/memory.db     chat_sessions(会话 + 提示词分段) + chat_memories(提取的记忆)
  data/dev_audit.db  dev_records(召回 / 提取监控)

【闭环】
  搜索侧存的拆解 → 对话侧注入或召回时读回来答题
  对话侧提取的记忆 → 下次对话进索引、被召回补回上下文
```

原来「仓库记忆」和「搜索历史」是两个库、信息高度重复（同一份拆解每次搜索各抄一份），已合并成一个库两张表，用 full_name 挂钩、拆解同一语言只存一份（不每次搜索都抄）。存储落在 `data/history.db`。

拆解按语言分开存：一个仓库还是占一行，但那份拆解里存的是「中文那份 / 英文那份」两格，中文搜存中文那格、英文搜存英文那格，互不覆盖。取的时候按当前搜索语言取对应那格，没有那格就当没存过、照常重新深挖出这门语言的版本。所以英文界面搜到一个之前只中文拆过的仓库，会重新拆出英文版，结果页语言不混。老数据没有语言标记，读的时候一律当中文那份。

```text
hunter/history/                       # 搜索侧记忆的代码
├── __init__.py                       # 门面：两个子模块的对外函数
├── history_db.py                     # 共享 history.db 连接（DB_PATH + _connect + now_str）
├── repo_memory.py                    # 仓库账本：一仓库一行，拆解按语言分格存（中/英各一份）
└── runs.py                           # 搜索账本：一次搜索一行，拆解指向 repo_memory

data/history.db                       # 搜索侧的库，repo_memory 和 runs 两张表都在这
```

对话侧（S2 聊天 + S3 记忆）另起两个包和一个库，各节自己的树里画：`hunter/chat/` 管对话循环，`hunter/memory/` 管对话侧存储和提取，都连 `data/memory.db`，跟搜索侧的 history.db 彻底分开。





### S1 Repo 记忆

只存事实、存到拆解为止：拆解对未来同语言的搜索有效，同一语言存一份；hit/miss、辩论结论绑定当次需求，按次留在搜索账本。静态假设，拆解一次终身有效、不做过期，只是分中英两格各存各的。被 gate 跳过的仓库也占一行只记跳过原因。复用发生在召回之后，命中有当前语言那格拆解才跳 explorer，gate、克隆、辩论照跑，事实拿现成的、判断重新做；命中的是别的语言那格就当没命中、重新深挖。记忆开关只挡读不挡写，关一次也不漏存。

两张表分工：**仓库账本**一仓库一行，存跨搜索不变的贵拆解（按语言分中英两格、各存一份），seen_runs 记这仓库被哪几次搜到过的摘要当审计时间线；**搜索账本**一次搜索一行，results 里每个仓库只留那次的轻量增量（判定、trace、tokens），拆解不抄、只留 full_name 指向仓库账本，回放时按那次搜索的语言 JOIN 回对应那格拆解。

按序读三个文件：

1. `history/history_db.py`：数据库其实就是磁盘上一个文件 `data/history.db`，读写它得先打开、建一条通道（叫连接），完事关掉。`_connect` 就负责打开这个文件、返回一条连接，两张表都来这里拿，不各写一遍。时间戳也在这统一：`now_str` 出「2026-07-07 12:50:22」这种可读格式，两张表的时间列都用它，开库直接看得懂。

2. `history/repo_memory.py`：仓库账本，管拆解的存取。
   - `upsert_repos`：搜完把这批仓库写进来，拆解写进当前语言那格、别的语言那格原样保留，分四种情况：
     - 头回见新建
     - 这门语言那格已存过拆解，只往 `seen_runs` 时间线追一笔
     - 这门语言那格还没拆解（新仓库、只有别的语言、或上次跳过），这次拆了就把这格补上
     - 这次没拆只记一笔。
   - `load_memories`：搜索侧拿一批仓库名查回谁有拆解，命中就跳 explorer。
   - `get_dissections`：搜索账本回放时按名字捞拆解。
   - `list / get / delete / clear`：撑前端仓库页。
   
3. `history/runs.py`：搜索账本，管每次搜索的流水账。
   - `save_run`（唯一写入口）：先插一行搜索拿 `run_id`，把每个仓库里重复的拆解摘掉、只留仓库名指向仓库账本，再回调 `upsert_repos` 写仓库账本。
   - `get_run`：回放时把拆解按名字 JOIN 回来拼成完整结果，仓库删了那格给空、不报错。
   - `list / delete / clear`：撑前端历史页。

接入点都在搜索侧：`repo_detection/content_filter.py` 用 load_memories 查记忆、命中的把拆解传给 explore_one 跳过 explorer（use_memory 开关只挡这步读），`pipeline.py` 搜完调 save_run 一次写两张表（不受开关影响），`webapp/backend/server.py` 启动调 init_runs + init_repo_memory 建表，/history 五个路由走搜索账本、/memory 四个路由走仓库账本。



> **示例：输入 keypoints 查询「多agent项目 / 有垂直领域应用 / 架构里有 agent ReAct 循环」，跑完 `save_run` 一次写两张表。**

仓库账本 `repo_memory`：

- 这次召回的十个仓库各占一行
- `dissection` 存着二十次工具换来的架构拆解，是最贵的东西，按语言分中英两格、同一语言只此一份
- `stars / size / language` 是仓库元数据
- `seen_runs` 记着这仓库被哪几次搜到过（run_id、时间、那次 keypoints、命中几条）
- `analysed_at / last_seen` 是可读时间。

![repo_memory 表](../img/repo_memory.png)



搜索账本 `runs`：这次搜索本身占一行，`keypoints / languages / top_k / cost` 是这次搜索的元数据，`results` 里每个仓库只留那次的判定、轨迹、token 这些按次不同的轻量增量，只留 `full_name` 指回上面那张表；`ts` 也是可读时间。

![runs 表](../img/runs.png)

同一个仓库的贵拆解在 `repo_memory` 按语言各存一份（中/英），`runs` 每次搜索只记那次的轻量账、**用仓库名指向 `repo_memory` **，不重复写入。回放某次搜索时 `get_run` 按名字、按那次搜索的语言把对应那格拆解 JOIN 回来拼全。



### S2 聊天模块

工作台右栏的对话。用户在结果卡点「+」把仓库注入右栏，问它问题，助手带着这些仓库的拆解流式回答。会话存进对话侧的库 `data/memory.db`，聊完能在会话列表里翻看、点开还原。

这一节讲的是对话的骨架和边界。骨架之上后来又叠了三样能力，各有专节：聊完自动提炼长期记忆（S3）、用户随口提到的仓库/记忆自动召回补进上下文（S4）、历史太长自动压缩（S5）。所以下面讲的一轮对话，实际走的是「先压缩判断 → 拼 system（含召回）→ 流式回答 → 后台提取和续笔记」这一整套，细节在后三节，这里先建立整体流程。

边界（始终成立）：对话和搜索完全解耦，对话不能触发搜索。搜一次是几百次模型调用的重活，不能被一句闲聊意外点火。没分析过、也没被召回命中的仓库，助手直接回「这个我没分析过，去搜索页跑一次」，绝不代替用户开搜索。

```text
hunter/chat/
├── __init__.py                  门面：导出 stream_chat
├── context.py                   拼 system：人设 + 记忆索引 + 注入仓库拆解 + 按需召回
├── session.py                   对话主循环：压缩、召回、流式回答、后台提取/笔记
└── skills/llm_skill.md          助手人设与边界纪律

hunter/memory/
├── memory_db.py                 共享 memory.db 连接
└── chat_history.py              chat_sessions 表：一会话一行存完整对话

data/memory.db                   对话侧的库，会话和提取的记忆都存这
```

按序读四个文件：

1. `chat/skills/llm_skill.md`：助手的人设和纪律，规定它是谁、怎么答、边界在哪（不触发搜索、没分析过的仓库让用户去搜索页、带「N 天前」的记忆是当时的观察别当实时状态咬死、分不清用户指哪个仓库就反问）。纯提示词，先读它就知道这个助手被设成什么样。

2. `chat/context.py`：拼给模型的开场资料（system），拆成带标签的段，不揉成一坨。段的种类：人设一段；长期记忆的索引一段（跨对话记住的事，每条只压一句摘要加「N 天前」，正文不进上下文、等召回用得上才补）；用户「+」注入的每个仓库的拆解各一段；再往后是召回补进来的段——用户嘴里提到但没点「+」的仓库拆解、相关记忆的正文、相关过往会话的笔记、分不清时的候选清单。发给模型时拼成整串，分段结构留给提示词监控分色。召回补入的段带「召回」标记，跟手动注入的区分开。

3. `chat/session.py`：对话主循环 `stream_chat`，一轮走这几步：先试压缩历史（到长度线才压，见 S5）；拿压缩后的历史让 context 拼好 system（拼之前先跑一次召回，见 S4）；开头吐一个 `prompt` 事件带上 system 分段和这轮消息给监控看；流式调 DeepSeek，边收边吐中性事件（一个字一个 delta、答完一个 done、出错一个 error），webapp 那层包成 SSE 推给前端；答完这轮，如果没触发压缩就在后台起两个任务——提取长期记忆（S3）和续写会话笔记（S5），都不阻塞回答、失败各自吞掉。

4. `memory/chat_history.py`：chat_sessions 表，一个会话一行，存这次对话从头到尾的完整消息（连库走 `memory/memory_db.py` 的共享连接，跟搜索侧的 history.db 彻底分开）。
   - `save_session`：upsert。同一会话再聊一轮，前端把完整快照发上来、整行覆盖；点新对话换个 session_id 就新插一行。
   - 会话 id 用创建时间戳（如 `20260703-1522`），一眼看出啥时候开的、也能排序。
   - `list / get / delete / rename / set_pinned`：撑会话列表的显示、还原、删除、改名、置顶。

示例：

- 用户把 TradingAgents 点「+」注入，问「反思怎么实现的」。context 把 TradingAgents 的拆解拼进 system，模型带着拆解流式答出实现细节。聊完在后台把这轮的重点提炼成长期记忆、把对话摘要续进会话笔记，会话本身存进 chat_sessions，列表里能看到、点开能还原。
- 用户又问「那个金融的 agent 项目怎么样」，虽然没点「+」，但召回从存过的仓库里挑出相关的补进上下文，助手照样能答（见 S4）。真提一个库里从没有过的仓库，召回全空，助手照边界回「去搜索页跑一次」。

提示词监控：点对话框里 agent 的头像，展开看这一轮真正发给模型的完整提示词，按板块分色。前端存下每个会话最近一次的 `prompt` 事件，点头像就按块渲染，人设、每个注入仓库、user 消息、assistant 消息各配一个固定颜色。注入的每个仓库拆解单独一块，一眼看清这轮给模型喂了什么。

### S3 记忆提取

每聊完一段，后台自动把对话里「值得长期记住、又没法从项目现状推导」的东西提炼出来存进记忆库，下次对话自动带上。存四类：user / feedback / project / repo（关于某个具体仓库的事实，带锚点）。

S3 压在 S2 建好的地基上：`memory_db.py`（对话侧连接）和 `chat_history.py`（chat_sessions 表）都是 S2 的，S3 直接用，只在 chat_sessions 上加一列 `extract_cursor` 记提取到第几条了，再新建一个 `extract/` 子包和一张 chat_memories 表。

```text
hunter/memory/
├── memory_db.py                 （S2 已建）共享 memory.db 连接
├── chat_history.py              （S2 已建）chat_sessions 表；S3 在它上面加一列 extract_cursor
└── extract/                     S3 新建
    ├── __init__.py
    ├── secret_scan.py           落库前密钥扫描打码
    ├── chat_memories.py         chat_memories 表：按 action 落库 + 各种查 + 游标存取
    ├── extractor.py             提取编排：攒轮触发、调模型、校验、落库，同时只跑一个不撞车
    └── skills/extract_memories.md

data/memory.db                   对话侧的库：S2 的 chat_sessions 表 + S3 新加的 chat_memories 表
```

按序读 S3 新增的三个文件：

1. `extract/secret_scan.py`：密钥防线。`scan_and_redact` 拿一段文本，用一组高置信度前缀正则（sk-ant、ghp_、AKIA 那些）扫，命中就换成 `[REDACTED]`。每条要落库的记忆正文先过它，防对话里贴的 API key 被存进库。
2. `extract/chat_memories.py`：管 chat_memories 表，一条记忆一行。
   - `apply_actions` 把模型返回的动作落库（add 插、update 按 name 找行覆盖、delete 按 name 删）。
   - `list_general` 取三类通用记忆（user、feedback、project，注入时全量带上）
   - `list_by_repo` 按仓库取 repo 类
   - `list_manifest` 列已有记忆的名字加描述（提取前给模型防重复）
   - `get/set_extract_cursor` 读写 chat_sessions 上那列游标

3. `extract/extractor.py`：编排。`spawn_extraction` 每轮聊完起个后台任务，攒够 12 条新消息（6 轮）或用户说「记住」才真跑，一次提取按顺序走：
   - 读游标只取新增消息，拼上已有记忆清单发给模型，拿回 JSON 动作。
   - repo 类的 full_name 去 history 仓库账本核真假、编的丢；每条正文过密钥扫描。
   - `apply_actions` 落库。
   - 落库成功才把游标挪到最新（失败就不挪、下次从老位置重来，不漏）。

   另外有一条防并发的规矩，用大白话讲就是：同一时刻只让一个提取在跑，别让两个同时往记忆库里写、打架。如果一个提取正跑着、这时你又聊完一轮触发了新的，它不插队开第二个，而是先记一个「待办」；等当前这个跑完，再补跑一次把待办里新聊的那段处理掉。这样既不会两个撞车，也不会漏掉最后那轮。


**存储逻辑（记忆在库里怎么摆）**：所有提取出的记忆全存进同一张 chat_memories 表，不分 session 建表。每行有一列 session_id 记它出自哪次对话，这列只是审计元数据，用来查「这次对话产出了哪些记忆」（`list_by_session`，给开发者面板看）。

真正用起来是跨 session 的：四类通用记忆每次对话全量注入，不管它当初在哪个 session 提取的；repo 类按仓库名注入。所以助手在一个全新会话里也知道你在别的会话说过的偏好，这正是记忆的意义。

去重也是全局的，记忆按 name 唯一，两次对话提出同名记忆后一次 update 覆盖前一次；提取前给模型的已有清单也是全库的，防跨 session 重复。一句话：**存一起、session_id 只当审计标签、召回全程跨 session。**

会话 id 直接用对话创建的时间戳（如 `20260703-1522`），不用随机串，一眼看出这次对话是什么时候开的、也天然可排序。chat_memories 的 id 是内部自增行号、不带含义，一条记忆真正的身份是它的 name；下面示例只看有意义的列。

示例：一条记忆怎么跨会话被用上。

第一步，7 月 3 日下午开了个对话（会话 `20260703-1522`）。你注入 TradingAgents、问它反思怎么实现，来回聊了 6 轮。攒够 6 轮，后台提取触发：它从这 6 轮里抠出一条关于 TradingAgents 的事实，落进 chat_memories。落库前先去 history 仓库账本确认真有这仓库、再扫一遍没夹带密钥。模型返回的就是这一条：

```json
{"action":"add","type":"repo","name":"tradingagents-reflection",
 "description":"TradingAgents 反思机制的实现方式",
 "content":"反思用轻量模型对已结算决策生成反思文本，追加进决策日志",
 "full_name":"TauricResearch/TradingAgents","where":"tradingagents/graph/reflection.py:Reflector"}
```

第二步，7 月 7 日上午另开一个对话（会话 `20260707-0910`），跟 TradingAgents 毫无关系。你说「我在找能写进简历的项目」。后台照样提取，抠出一条关于你的事实：一条 user 类记忆。

现在 chat_memories 表里躺着两条，来自两次不同对话：

| 创建时间 | type | name | content | 出自会话 |
|---|---|---|---|---|
| 07-03 15:22 | repo | tradingagents-reflection | 反思用轻量模型…追加进决策日志 | 20260703-1522 |
| 07-07 09:10 | user | user-goal-resume | 用户在找能写进简历的项目 | 20260707-0910 |

第三步，你开一个跟前两次都无关的全新对话。拼给模型的 system 里，三类通用记忆（user / feedback / project）全量带上，所以第二行那条「用户在找简历项目」被带进来了，哪怕它是 4 天前在另一个对话里提的。助手于是知道你的目标、推荐时往简历项目靠。如果你在这个新对话里也注入了 TradingAgents，第一行那条 repo 事实会跟着 TradingAgents 的拆解一起注入。

从头到尾，「出自会话」那列没参与这个过程，它只在开发者审计面板按会话分组看「哪次对话产出了哪些记忆」时才用到。





### S4 记忆召回

S2、S3 攒下了 history 里几十个仓库的贵拆解，和 chat_memories 里 extract 下来的长期记忆。

现在我们不光希望手动「+」来注入 repo 拆解记忆，我们同事还希望可以用户随口提了一句 “炒股类 agent” 就能判断出指的是 Tradingagents 的项目并且自动注入上下文。

此外，extract 的四类通用记忆每轮全量塞十分浪费上下文，涨到几百条就是纯浪费加噪声，S4 让 system 里常驻的只有轻的索引，重的正文等这轮用得上才选择性看原文去捞。



> **每轮 system 的构成**

**常驻（每轮都有，都很轻）：**

- `llm_skill.md` 基础人设
- 三类通用记忆（user / feedback / project）索引，「类型、名字、几天前记的、一句描述」。助手靠它知道自己记得哪些事，正文不在这。几十条也就一两 KB，涨到几百条也塞得起，重的是正文

```python
- [user] user-goal-resume（4 天前）：用户在找能写进简历的项目
- [feedback] reply-terse（12 天前）：回答别铺垫，先结论再细节
```

- 用户点「+」注入的仓库全量拆解（含之前召回转正的，见下）

**按需（挑选器判定这轮用得上才补）：**

- 用户提到的仓库的全量拆解
- 相关记忆的完整正文
- 分不清时的候选清单，给反问用

**挑选器 + system prompt 注入**

用户每发一条消息，**先用小模型跑一次挑选，再拼 system 调主模型答话**。挑选是一次几百 token 的小调用，多等一秒，换每轮只带相关内容。

- 跳过门：消息去掉首尾空白不足 4 个字，或是纯应答（「嗯」「好的」「ok」），不跑，省下调用。CC 判「没空格就是单词消息」，英文才成立，中文整句没空格，改成字数加应答词表。
- 输入带最近 3 条消息。
- 清单两类条目混在一份里，一行一条。仓库条目是「全名、拆解的用途摘要、关键设计名当标签」，已在注入名单里的不列；记忆条目是「名字、一句描述」。描述就是召回的搜索面，S3 的提取提示词已要求 description 写成一句能被搜到的摘要，这里正好接上。**（这里没看懂待解释）**
- 匹配靠意思不靠字面。用户说「有个股票分析的智能体」，清单里 TradingAgents 那行写着「多智能体 LLM 金融交易框架，对给定的股票产出买卖决策」，模型对得上；字符串匹配对不上，所以挑选必须是一次模型调用，不是本地关键词过滤。
- 输出三档，强制 JSON：`repos`（有把握的仓库，最多 3 个）、`memories`（相关记忆，最多 5 条）、`ambiguous`（几个仓库都沾边分不清）。
- 只挑清楚有用的，拿不准就不挑，三个列表全空是常态不是失败。错捞一个仓库等于拿无关拆解污染回答，比漏掉更糟。返回的名字对清单核一遍，编造的丢掉；调用失败、解析不出，一律当空结果。

**挑选器命中后：**

- 仓库命中：全量拆解补进这轮 system，同时这个仓库转正，前端右栏自动冒出一个标「召回」的芯片，往后每轮跟点过「+」一样常驻，用户不想要随手删。转正解决连续追问：下一轮问「它架构呢」不用再靠挑选器认出「它」。
- 记忆命中：完整正文补进「召回的记忆」一段，每条带「N 天前记的」。
- 歧义：不注全量，注一小段候选清单（一行名字加一句描述），主模型看到就反问。
- 全空：什么都不补，索引还在，助手照常答。

时间一律标「N 天前」，不用原始日期。模型不擅长日期算术，看见「2026-05-12」不会起疑，看见「56 天前」才会想到可能过时。



> **文件结构**

挑选器独立成 memory 下的一个子包，拼 system 的 context/session 还在 chat：

```text
hunter/memory/recall/          S4 新建
├── recall.py                  挑选器
└── skills/recall_memories.md  挑选器提示词

hunter/chat/
├── context.py                 （S2 已建）改：通用记忆从全量正文换成索引，拼 system 前先跑召回
├── session.py                 （S2 已建）改：把最近几条消息递给召回，命中的仓库通知前端转正
└── skills/llm_skill.md        （S2 已建）加：反问、记忆过时两条纪律
```

按序读四个文件：

1. `memory/recall/recall.py`：挑选器本体，核心是通用接口 `select_from_manifest`：给一份「名字加描述」的清单和最近几条消息，回三档结果。跳过门、挑选调用、名字校验、失败兜底全在这。它不认「仓库」这个概念，给什么清单挑什么，以后 compact 笔记也走它。

2. `memory/recall/skills/recall_memories.md`：挑选器的提示词，四块内容：
   - 任务：给你最近几条对话和一份清单，清单一行一个条目（可能是仓库、记忆或过往会话的笔记）带一句描述，挑出对回答用户当前这条消息明显有用的。
   - 铁律：靠描述的意思对，不靠名字字面像；只挑清楚有用的，拿不准就不挑，全空正常；几个都沾边分不清，放 ambiguous 别硬猜；只准输出清单里有的名字。
   - 输出格式：`{"picks": [], "ambiguous": []}`，纯 JSON，别的什么都不带。picks 是挑中的名字（仓库、记忆、笔记混在一个列表里，不分类型，由代码事后按名字分辨），ambiguous 是分不清指哪个的候选。
   - 四个例子：语义命中（「股票分析的智能体」挑中描述含金融交易的 TradingAgents）、歧义（「金融的 agent 项目」两个都像，进 ambiguous）、记忆命中（「接着上次说的部署方案聊」挑中那条部署记忆）、全空（「谢谢」什么都不挑）。

3. `chat/context.py`：拼 system 的改造。四类通用记忆那段从全量正文换成索引；拼仓库段之前先调挑选器，按三档补段。补入的段带「召回」标记，提示词监控靠它分色。

4. `chat/session.py`：对话主循环的改造。从对话历史里取最近几条消息交给拼 system 的流程；仓库命中时在事件流里多吐一个转正通知，前端收到补芯片。

`llm_skill.md` 加两条纪律：

- system 里出现「用户可能提到这些仓库」候选段、你从对话里分不清指哪个，反问确认，列出候选让用户挑，别猜一个开答。
- 索引只是记忆的一句话摘要，正文没补进来的别硬编细节；带「N 天前」的记忆和拆解是当时的观察，可能过时，别当实时状态咬死。

**监控**：挑选器每次决策记进开发者抽屉（🔬），没跑记跳过原因，跑了记给了什么清单、模型原始返回、三档各挑了谁，跟 S3 提取监控同一套路。提示词面板里召回补入的段标「召回」，跟「+」注入的分开色，一眼看出这轮哪些是系统自己捞的。

**跟 CC 的对应表**

照搬：

- 双层结构：索引常驻加正文按需（CC 的 MEMORY.md 索引加记忆文件）
- 挑选纪律：只挑确定有用、拿不准不挑、空是常态、有上限
- 清单格式：一行「类型、名字、时间、描述」
- 名字校验丢编造、失败当空结果
- 「N 天前」时间标注加过时提醒

魔改：

- 跳过门中文化：空格判单词改成字数加应答词表
- 两档改三档：加歧义档给反问，CC 没有反问
- 挑选输入从最后一句改成最近 3 条：CC 的召回结果留在对话记录里，我们每轮重拼，短窗口保住追问
- 命中仓库显式转正成芯片：同上一条的原因，转正后它常驻、追问不再依赖挑选器

不搬：

- 异步预取（CC 让挑选和主回答并行跑，答完插进对话记录）：它的主循环带工具、能中途插内容；我们一发一收，召回必须在发请求前就位，只能先挑后答
- 会话字节预算：单用户几十个仓库，量到不了
- 正在用的工具不召回其文档：我们对话没有工具
- 索引下线实验：CC 有个开关在试「索引不再常驻、全靠召回」，它敢是因为模型能拿工具自己翻记忆文件兜底；我们的助手没工具，挑选器漏了就全盲，索引必须留

keypoints（seen_runs 里历次搜索的需求原文）不进清单：它是「用户当初为什么搜到它」，比描述和标签噪，一提「金融」就把所有沾过金融需求的仓库全捞出来。留作以后描述加标签都对不上时的兜底。

**笔记也走这个口（已实现）**：`select_from_manifest` 是通用底座，不认条目类型。有笔记的过往会话（S5 压缩层攒的会话摘要）也列进清单，每条是「会话名加一句简介」，挑「哪次旧对话跟当前问题相关」。命中就把那次对话的笔记正文补进「召回的会话笔记」段，跟召回的记忆分开成一段。所以现在清单里混着三类条目：仓库、记忆、会话笔记，挑选器一视同仁，代码拿回名字后按它属于哪类分派。

示例，一条消息进来的完整走法。用户注入着 TradingAgents 在聊，发来「跟 MetaGPT 比哪个适合写简历」：

1. 跳过门放行（够 4 个字）。
2. 挑选器收到最近 3 条消息和清单，清单里有 MetaGPT（TradingAgents 已注入所以不列）和十几条记忆。
3. 返回 `{"picks": ["FoundationAgents/MetaGPT", "user-goal-resume"], "ambiguous": []}`（仓库和记忆混在 picks 里，代码按名字分辨出前者是仓库、后者是记忆）。
4. system 里补进 MetaGPT 的全量拆解和「用户在找能写进简历的项目（4 天前记的）」，助手比较两个仓库、往简历角度靠。
5. 前端右栏冒出标「召回」的 MetaGPT 芯片，下轮追问「它的 SOP 怎么实现的」直接命中常驻拆解；🔬 抽屉里能看到这次挑选的完整进出。

另两条走向：用户说「那个金融的 agent 项目」，两个仓库都像，挑选器进 ambiguous，助手反问「做股票交易决策的 TradingAgents，还是金融分析的 FinRobot？」；用户提一个库里没有的仓库，挑选器全空，助手照边界回「去搜索页跑一次」。

落地分三步：先建挑选器和它的提示词，独立成块，拿假清单就能单测三档；再接进拼 system 的链路（索引化、召回补段、传消息），动的是 S2 在跑的文件，改完真机回归；最后前端转正芯片、监控分色、🔬 渲染，加 llm_skill 两条纪律。



### S5 会话压缩

设一道 token 长度线，没到线什么都不做，到线就把偏旧的历史换成一份笔记或摘要，最近几轮原样保留，让对话像没断过一样接着聊。

**分两层，一层平时悄悄准备、一层到时候真正动手：**

- 笔记层在后台跑，每聊完一轮检查一次，攒够几轮就把笔记重写一遍，不管这次会不会触发压缩，先把料备好、不占对话时间。
- 压缩层只在长度真的到线那一刻才执行替换，优先用笔记层备好的现成笔记（零成本），笔记不可用就现场调一次模型写摘要，这步也失败就硬砍最老的几轮保底，绝不让对话卡死发不出去。

```text
hunter/memory/compact/                # S5，对话侧压缩，跟 extract、recall 并列
├── __init__.py                       # 门面：对外导出的入口函数
├── tokens.py                         # 量尺：按字符数估一段对话大概值多少 token
├── note.py                           # 笔记层：后台悄悄把聊过的压成一份笔记存库
├── fallback.py                       # 兜底：笔记不可用时现调模型写一份摘要
├── compact.py                        # 压缩总编排：到线判断、笔记优先、兜底次之、硬截保底
└── skills/
    ├── session_note.md               # 笔记模型的提示词
    └── compact_fallback.md           # 兜底摘要模型的提示词
```

按序读五处，先量尺，再笔记，再兜底，最后是把三者串起来的总编排：

1. `compact/tokens.py`：一把量尺，接的是 DeepSeek 真实分词器，算出来的 token 数是准的。分词器文件首次用时从 HuggingFace 下一份缓存进 `data/`，之后直接读缓存不再联网；下载或加载失败就退回按字符估算的老办法（中文一个字当一个 token、其余四个字符抵一个，往大了估更安全），不让这把尺子因为一时拿不到词表就用不了。压缩要不要做、压完够不够短，全靠这把尺子量，后面几个文件都问它要数。

2. `compact/note.py`：笔记层，纯后台活，跟压缩会不会触发没关系，平时就在悄悄准备。每聊完一轮检查一次，把游标（笔记已经覆盖到第几条消息了）之后的新消息拿 `tokens.py` 估一下大概多少 token，够 `NOTE_TOKEN_THRESHOLD`（1,500）才触发重写，不够就跳过继续攒，下一轮接着测这段累积的新消息。触发时把上次的旧笔记和这段新消息一起喂给模型，重写出一份新的完整笔记（是整份重写，不是往后接字），连同游标和一句简介一并存进库里。按 token 量触发是为了两头都不浪费：都是短闲聊时字数一直攒不到线，不会为几句「嗯」「好的」就烧一次模型调用；单轮内容很密（贴了大段代码、长篇讨论）时不用凑够特定条数，几条就能过线立刻触发。跟提取记忆同一套规矩：同一会话同时只跑一个笔记任务，跑着时又聊完一轮就先排队，跑完再补一次；写失败不影响对话，下次从老游标接着来，不会卡住也不会重复。笔记攒好放在库里，等真正要压缩的时候直接捡现成的用。

3. `compact/fallback.py`：备胎，只有笔记层派不上用场（还没攒够，或者跟当前对话对不上）压缩又必须发生时才会用到。现场调一次模型，把从头到尾的完整对话直接总结成一份摘要。为了让模型写得靠谱，先在一个隐藏的草稿区里把对话捋一遍思路，再落一份正式摘要；草稿只是给模型自己想清楚用的，最后只把正式那份塞回对话，草稿不占地方。这条路比笔记贵，是现场现算的，只有笔记不能用时才走。

4. `compact/compact.py`：总指挥，决定压不压、怎么压。每次回答前先拿 `tokens.py` 量一下这轮对话有多长，不够长直接放行，什么都不做。到了长度线，第一选择是拿 `note.py` 存好的笔记顶替旧消息，免费、笔记现成；笔记没有或者对不上，退一步现调 `fallback.py` 现写一份摘要；连这步都失败（比如模型这次没答出来），就不再花钱硬试，直接把最老的几轮砍掉、只留最近一段保底。如果一个会话连续好几次都得靠硬砍收场，后面干脆不再尝试笔记和摘要、直接硬砍，省得每次都白烧一次模型调用。不管走哪条路，压缩后消息数组变短了，原来数第几条的下标全部作废，提取记忆和笔记自己的两个进度游标都要跟着挪到压缩后的新长度，不然回头会重复提取、或者把这条自己写的说明当成真实对话又压一遍。

   压缩靠三个数字管着，各管一件事：

   - **触发线 `COMPACT_THRESHOLD = 40_000`**：对话攒到多少字数（token，可以粗略理解成字数）才要压缩，没到这个数什么都不做，攒够了才动手。
   - **保留段下限 `KEEP_MIN_TOKENS = 4_000` 和 `KEEP_MIN_MSGS = 4`**：压缩后，最近这一段要原样保留、不浓缩进笔记的内容，字数不能少于 4,000、条数不能少于 4 条，两条必须同时满足；差哪个就往前多留一条消息，直到两条都够为止。这是为了保证压缩完之后 AI 手头留着的最近对话，既不能太短也不能条数太少，不然接不上话。
   - **保留段上限 `KEEP_MAX_TOKENS = 16_000`**：往前多留也不能没边，留到这个数就立刻停手，哪怕上面两条下限还没凑够，为的是防止保留段自己也变得太长，失去压缩省地方的意义。

   这三个数字都只算对话历史（`user`/`assistant` 消息数组本身），不含 system prompt。system 是压缩跑完之后才由 `chat/context.py` 另外拼的（人设、记忆索引、注入仓库的拆解、召回段），这部分不管多大都不计入这条线，也不受这套压缩逻辑管。真正发给模型的总量是「system（不受控）+ 压缩后的对话历史（被这三个数管着）」。

5. `skills/session_note.md` 和 `skills/compact_fallback.md`：分别是 `note.py` 和 `fallback.py` 喂给模型的提示词。两份都要求整理成固定的五段（用户目标、聊过的仓库与结论、关键信息与决定、用户原话要点、当前话题与待办），尤其强调用户自己说过的话、改过的主意一个字都不能丢，这是最容易漏、漏了也最难补的部分。笔记那份多让模型顺手写一句简介，这句以后要给 S4 召回判断「这次旧对话跟当前问题搭不搭边」用。

接入点在 `chat/session.py`：每轮回答前先调 `maybe_compact` 试压缩，压过的历史才拿去拼 system、发给模型；这轮聊完再各自起一个后台任务，`spawn_note` 续笔记、`spawn_extraction` 提取记忆，两者互不干扰。压缩这一步走的是 `extract` 那档模型（兜底摘要用它）。`webapp/backend/server.py` 启动时调一次 `init_notes`，给 `chat_sessions` 表补上笔记要用的三列，排在建表之后。

前端有个配套的可视化：每轮答完，后端把这轮历史实际占了多少 token、离压缩触发线多远，随事件流带给前端；点对话框里 AI 的头像，提示词面板顶部有一条上下文占用条，显示当前占用百分比，越接近触发线颜色越深，压缩发生的那一轮条子会明显跌回去。用户能直观看出「还能聊多久才会压缩」，不用猜。

> **示例：**

一个用户跟 AI 已经聊了 30 轮（一问一答算一轮），消息数组攒到了第 60 条。系统估算一下这 60 条消息一共占多少字数（token 是衡量文字量的单位，粗略理解成字数就行），算出来是 41,200，超过了触发压缩的门槛 40,000，于是判定这轮要压缩。

压缩要解决的问题是：早期聊过的内容没必要原样留着占地方，浓缩成一份笔记就够了；只有最近聊的几轮要原样保留，好让 AI 接得上话。系统平时会在后台悄悄把聊过的内容浓缩写成一份笔记，这次这份笔记已经写到了第 54 条消息（"写到第几条"这个进度标记就是笔记的游标）。压缩这次优先用这份现成的笔记去顶替第 1 到 54 条，不用现场再调一次模型去总结，省钱。

问题是：笔记只覆盖到第 54 条，如果直接拿"笔记 + 第 55 到 60 条原样保留"拼成压缩结果，这 6 条原样保留的消息够不够让 AI 接得上话？系统设了两条最低要求，必须同时满足：

- **`KEEP_MIN_MSGS`（原样保留的消息条数不能少于几条）**：门槛是 4 条。第 55 到 60 条已经有 6 条，这条满足了。
- **`KEEP_MIN_TOKENS`（原样保留的内容字数不能少于多少）**：光条数够不算数，万一这几条都是"嗯""好的"这种短话，字数太少 AI 照样接不上话。这条门槛是 4,000。第 55 到 60 条这 6 条一共只有 2,600 字，没满足。

字数不够，系统就把笔记已经覆盖过的部分也往回借一点，一条一条往前多留：先把第 54 条也纳入保留段（+900，累计 3,500），还是不够；再把第 53 条也纳入（+950，累计 4,450），这下超过了 4,000 这条门槛，停止往前借。

最终原样保留的是第 53 条到第 60 条，一共 8 条消息、4,450 字。因为笔记本来就覆盖到第 54 条，这次往前借用了第 53、54 两条，这两条消息就变成了"既被浓缩写进了笔记里，又原样留在保留段里"，有一点点重复，但这是为了保证 AI 接得上话必须付出的代价。

往前借也不是没有上限的。系统还设了一条 `KEEP_MAX_TOKENS`（往前借最多能借多少字数），门槛是 16,000。这次一路借到 4,450，远没碰到这条上限。但假如这几条消息里有一条贴了一大段日志、单条就占 12,000 字，往前借的时候一算超过了 16,000，系统会立刻停止借用，哪怕这时候 4 条或 4,000 字这两条最低要求都还没凑够——这是为了防止保留段自己也变得太长，失去压缩省地方的意义。

压缩做完后，原来的 60 条消息被换成了：一条"笔记摘要"消息，加上原样保留的这 8 条，一共 9 条，比原来 60 条小了一大截。同时，系统会把"笔记写到第几条""长期记忆提炼到第几条"这两个进度标记都重新对齐到压缩后的新长度，这样下一轮接着聊的时候，不会把这条自己拼出来的"笔记摘要"消息误当成真实聊天内容，又重复拿去提炼一遍。

## 双语支持

界面能切中文和英文，切了之后要求全链路一致：选英文就全英文、不冒中文，选中文反之。这件事靠一个语言参数从界面一路传到底，凡是会产出用户看得见的文字、或会插进发给模型的提示词的地方，都跟着这个参数走。这一节把它贯穿的地方集中讲，前面各阶段不再重复。

语言参数从哪来：前端界面语言（中文界面发「简体中文」、英文界面发「English」）跟着搜索请求和对话请求一起发给后端，后端一路往下传。这两条链各自要覆盖的点：

**搜索侧**（一次搜索）——凡是模型产出的、或会显示给用户的自然语言都按语言写：
- 判定标准（把用户模糊需求编译成的那句可判定标准）：英文搜就出英文标准，它既回显给用户看，也拼进后面辩论的提示词。
- gate 跳过理由：显示在结果卡片上，跟着语言走。
- 拆解、辩论各方的论据和裁决理由：这些散文字段按语言写。
- 深挖循环里所有注入模型的固定文案：逼停、半程/停滞提醒、JSON 修复重试、锚点重修指令，还有四个工具的返回文案（「文件不存在」「无命中」这些）和工具本身的说明——这些用户看不到、只有模型在深挖过程中看，但英文搜索时插一段中文容易把模型的英文输出带偏，所以也全按语言走，中英各备一套（集中放在 `repo_detection/prompt_text.py`，按当前语言取对应那套）。
- 拆解按语言分格存（见前面搜索侧记忆节）：英文搜命中的若是中文拆解，当没命中、重新拆出英文版，结果页不混语言。

**对话侧**（一轮聊天）——助手回答语言，以及拼进 system 的所有包装文案：
- 人设最后一句直接规定用哪种语言回答，这是助手回答语言的总开关。
- 拼 system 的各段标签和固定措辞（记忆索引标题、召回段标题、「N 天前」这类时间表述等）按语言写。
- 压缩时插进历史的那条说明消息、后台重写的会话笔记、兜底摘要、提取出来的长期记忆正文，全按当前对话语言写。

一个有意的取舍：库里存量的中文记忆、旧笔记、旧拆解不做翻译迁移。它们作为材料喂给模型时，模型会用当前语言转述，用户看不到原文；笔记和拆解各自会在下次重写/重新深挖时自然切成新语言。所以「切了语言之后新产生的东西全对，存量不强行翻译」是这套设计的边界。

## 基础设施

搜索侧和对话侧底下垫着几个横切的支撑件，它们不属于任何单个阶段，前面各节都在用它们、只是没单独展开。

- `config.py`：一处集中管三样东西——各个密钥（GitHub token、模型 key）、每个阶段用哪个模型的名字、按名字读磁盘上的 skill 提示词文件。密钥前端填一次、运行时注入，不写死在代码里。哪一步该用哪个模型、该读哪份提示词，全从这里取。
- `cost.py`：token 计量。每次调模型都把这次花掉的 token 记一笔，按阶段汇总，跑完看得出钱花在哪。深挖一个仓库十几万 token，靠它才知道分布。前面各节反复出现的「记一笔用量」都是它。
- `dev.py`：开发者监控。把每轮背后用户看不到的动作（拼了什么 system、召回挑了谁、提取出什么、压缩压了多少）记下来，供前端审计视图翻看。默认关，横切主流程但不改主流程。
- `dev_store.py`：把上面 dev.py 记的监控落到磁盘库里，重启还能翻，不是只留在内存里。
- `visual.py`：notebook 里用的展示件，跑完把成本和排序结果摆成表格看，跟正式网页流程无关，命令行或 notebook 跑实验时才用。
