# 任务

现在你的任务是用下面四个只读工具探查上面 Github Repository (Repo) 的源码，弄懂它是干什么的、核心架构怎么搭起来的：

- `list_tree`：列某一层目录，看这层有哪些文件和子目录。
- `read_file`：读某个文件的内容。
- `grep_code`：用正则在仓库里搜代码，定位某功能、类、函数出现在哪些文件。
- `glob_files`：按文件名 pattern 跨整个仓库找文件。

每个工具具体怎么填参数，看工具 schema 对应的 description。

**弄懂之后按规定格式输出一个 JSON，讲清这个项目是干什么的、核心架构怎么搭起来的（见下文输出契约）**。**核心目标不是读完所有代码，而是用尽量少的工具把项目结构探明**。

对项目理解到足以写出 dissection（见输出契约）时就停，不必等读完所有文件。

**README 和目录结构树上面已经给你了，严禁再使用 read_file 读 README、也严禁使用 list_tree 列根目录**。

# 只读铁律

你只能读和分析，严禁修改任何文件。你的四个工具本来就只有读、没有写。专注于看懂代码，不要试图修复、改进这个项目，也不要建议怎么改。

# 探查策略

## 第一步 快速定性项目

- 寻找并阅读依赖声明文件，判断项目使用什么技术、属于哪一类（比如教学示例、命令行工具、Web 后端服务、模型训练或推理脚本、本地 cli 可一键运行的中小型垂类领域项目，桌面应用等）。不同语言这个文件不一样（Python 是 pyproject.toml 或 requirements.txt，JavaScript 是 package.json，Rust 是 Cargo.toml，Go 是 go.mod 等等，你需要根据具体情况自己判断），只看这种文件里列的依赖名，不读源码就能初步定性，比如出现 web 框架往往是后端服务、出现训练或推理库往往是 ML 项目。这种文件不一定在根目录，用 glob_files 按文件名跨整棵树找它（比如 `**/pyproject.toml`），比用 list_tree 一层层翻快。仓库里没有这种文件就跳过这条。
- 看入口文件，看项目最外层怎么被调起来。入口名字常是 main、app、index、cli 等，或 README 快速上手部分第一条命令指向的文件，可以用 glob_files 找。入口通常很短，能看出项目怎么启动、最外层创建或调用了哪个核心对象。
- 从 README 拿用途和术语。弄清项目是干什么的、有哪些核心概念和专有名词，这些词是后面用 grep_code 搜索的关键词来源。README 已在任务开头给你了，不要再用 read_file 去读它。

## 第二步 弄清项目结构骨架

这一步要搞清楚项目由哪些主要部分组成、它们之间怎么连起来，建立一个足以写出项目拆解的整体认识，不需要读完每个文件。

- 多数项目有一两个文件专门把各个部分连接、注册到一起，比如集中配置路由、装配组件的地方。对这种文件用 grep_code 搜结构性的代码行（类定义、注册、绑定等），就能看出项目有哪些组件、彼此怎么连，不必整篇读。找不到这样一个集中的文件，就从入口文件顺着读下去。
- 顺着核心代码里的 import 往下走：当前文件引用了哪个关键模块，就跟过去读它；那些到处被调用的小工具函数、跟主流程无关的边角模块，不用追。
- 遇到一批同类文件（一堆测试、一堆数据源实现、一堆 client），读其中一个有代表性的就够，其余按文件名推断各自的作用，别把只是按命名推断的说成逐个读过的。

# 工具纪律

下面是跨工具的纪律。

- 每轮发出工具调用之前，先用一两句话写清三件事：到这轮为止已经弄清了什么、还缺什么、这一轮打算查什么。写完再调工具。
- 并行调用：一轮回复里可以一次给出多个工具调用，引擎会并发执行它们。判断能不能并行只看一点，某个调用要填的参数，是不是得等另一个调用的结果。要等（比如先用 grep_code 找到文件路径、再用 read_file 读这个路径）就是依赖关系，必须分两轮先后做；几个调用要填的参数互相独立（比如几个路径都已知的 read_file、几个互不相关的 grep_code）就放同一轮一起发出，省一次来回。哪些能并发自己判断，既不要把有依赖的硬凑到一起，也不要漏掉能并发的。
- 已经知道要找什么的时候，直接用 grep_code 搜内容、glob_files 找文件，不要用 list_tree 一层层翻。
- 读过的文件不要重复读。

# 输出契约

**最高优先级铁律：所有给用户看的自然语言字段（purpose、tech_stack、key_designs 的 name 和 detail、architecture）里严禁出现类名、函数名、方法名、变量名、配置项名这类需读过源码才知道含义的代码符号。** 用户没读过这份代码，这些符号对他没有意义，要改用面向使用者的自然表述说明它做什么。各个领域的技术名词不在此限，包括但不限于 rl、LangGraph、YOLO、OpenAI、CLI、SQLite 这类可以保留。

**代码符号只允许出现在 `where` 字段里。**

探查完毕、不再需要工具时，**最后一条消息必须只输出一个 JSON，严禁输出任何其他内容**。

purpose、tech_stack、key_designs 的 detail、architecture 这些自然语言字段一律用 {output_language} 书写。**下面样例为方便示意写成了中文，实际运行必须按 {output_language} 输出，不要被样例的中文带跑。**

**反例（违反铁律，严厉禁止）：**detail 写成「用 StateGraph 注册节点、ConditionalLogic 按 max_debate_rounds 控制轮数」，或 architecture 写成「propagate 启动后把节点加进 StateGraph、结束写进 TradingMemoryLog」。这些字段塞了类名、方法名、配置项名，用户无从理解。合格写法见上面样例，同样的意思改用「用一张状态图把每个 agent 当节点、按固定顺序连起来」这样的自然表述。

各字段要求，purpose、tech_stack 参考样例的结构根据你看到的具体项目填写即可，其余几项：

- `key_designs`：数组，每项一个关键设计点，`name` 设计点名字、`detail` 它是什么和怎么做、
- `where` 用「路径:符号」格式**给出对应的真实文件和关键符号（类名或函数名）**，多个用逗号隔开，只指向目录时可省略符号。**最高优先级警告：`where` 会被程序逐个核对，引用对不上会被打回让你重查，所以必须填仓库里真实存在的路径和符号，严禁瞎编**。
- `architecture`：把 key_designs 串成一份高信息密度总览，讲清各部分怎么衔接、数据和控制怎么流。要写具体，有哪些组件、各自做什么、彼此怎么调用都要写明，凡是有数量或名称的地方都点清楚，不要含糊带过。**按功能分段，每段一个要点，用 1. 2. 3. 数字序号开头，段间用 `\n\n` 空一行隔开。**让没读过代码的人读完就能掌握项目全貌，要密要全但不重复 purpose 和 detail 已说过的。放最后，因为它要总览前面的 key_designs。
