# 任务

上面 system 给了这个仓库的资料和一份架构拆解。文末是一条需求,材料区可能还附了为这条需求从源码里抠出的相关片段。

基于这些材料,为「这个仓库满足该需求」找最强的支持证据。不用工具,只依据给你的拆解和源码片段判断。

# 取证规则

- 先看拆解的「关键设计」,每条带 `where`(路径:符号),这些锚点已被程序核验过、真实存在。跟需求相关的锚点就是最直接的支持证据。
- 材料区附的源码片段(如果有)是为这条需求专门抠出来的,是你坐实证据的一手依据,优先引它。
- `where` 填「路径:符号」,符号是类名或函数名,多个逗号隔开。它会被程序对源码逐个核验,核不上作废,严禁编造。只填拆解或源码片段里真实出现过的路径和符号。
- 找不到证据就如实写:`evidence` 写没找到,`where` 留空,`searched` 写你在拆解和片段里看了什么。严禁硬凑。
- 需求问项目整体是什么、属于什么领域、核心范式是什么(定性类)的,以 system 里的 README、description、topics 和拆解的 purpose、architecture 定位为证据,直接引它们的原话,`where` 留空,这类不用去源码找锚点。但只是问项目里「有没有某个具体功能实现」的,不算定性,仍要按上面的规则给源码锚点。
- 需求关于体量的(如「中小型」「轻量」)以体积数字为证据,关于热度的(如「star 多」)以 star 数为证据,直接引数字,`where` 留空。
- 需求若揉了多个意思(如「适合写进简历的中小型项目」含「适合简历」和「中小型」),当一个整体:任一意思找不到支持证据,整条按「没找到」处理,不要挑能证的那个充数。

# 输出

最后只输出一个 JSON,不要别的话。evidence 一句话、最多两句,细节靠 `where` 承载,不靠堆字。evidence 用 {output_language} 书写。

```json
{"evidence": "一句话证据,没找到就写没找到", "where": "路径:符号,可空", "searched": "没找到时写看过什么,找到了留空"}
```

正例,需求是「必须是多 agent」:

```json
{"evidence": "agents 目录下 12 个不同角色的 agent,由一个图统一编排。", "where": "tradingagents/agents/__init__.py:create_bull_researcher", "searched": ""}
```

正例,需求是「有完整的 eval 流程」而材料里没有:

```json
{"evidence": "没找到,拆解和抠出的片段里都没有独立评测脚本或指标计算。", "where": "", "searched": "看了拆解的关键设计和附上的片段,均无评测相关"}
```

反例(作废):evidence 写成一整段分点论述;`where` 填了源码里不存在的路径或符号。
