# 任务

给你一条需求(在文末)、一份这个仓库的架构拆解、四个只读工具(list_tree / read_file / grep_code / glob_files),工具读的是本仓库已下载到本地的源码。

为「这个仓库不满足该需求」找反证,或指出拆解说法的证据缺口,反证用工具到源码里坐实。

# 反证长什么样

逐个类型排查,任一命中就是反证:

- 空壳实现:锚点指的文件在,但里面只有几行样板或 TODO,没有实质逻辑。
- 只有示例没有实现:能力只出现在 example/demo/docs 里,主代码里不存在。
- 依赖声明了但没用:依赖清单里有那个库,grep 全库却没有实际调用。
- 数字冲突:体积或 star 数与需求直接矛盾(如需求要轻量,体积几百 MB)。
- 拆解与源码对不上:拆解宣称的能力,按锚点去看实物明显夸大或不存在。

# 取证规则

- 拆解的「关键设计」每条带 `where`(路径:符号),这些锚点已被程序核验过、真实存在。先 read_file 直达锚点,核实拆解的说法是否属实、有没有夸大;锚点覆盖不到的再自己 grep_code / glob_files 查。
- 拆解可能有错漏,它的说法不能直接当真。
- README 和根目录结构树已在上面给出,不要再用工具读它们。
- `where` 填「路径:符号」,符号是类名或函数名,多个逗号隔开。它会被程序对源码逐个核验,核不上作废,严禁编造。
- 找不到反证就如实写:`evidence` 写没找到反证,`searched` 写查了什么。严禁为反而反硬凑。
- 需求关于体量的(如「中小型」「轻量」)以体积数字为准,关于热度的(如「star 多」)以 star 数为准,数字与需求冲突就是反证,不用工具,`where` 留空。
- 需求若揉了多个意思(如「适合写进简历的中小型项目」含「适合简历」和「中小型」),逐个意思找反证:任一意思有反证,整条就算有反证。
- 工具最多 4 次,反证坐实或确认没有就停。

# 输出

取证完毕,最后一条消息只输出一个 JSON,不要别的话。evidence 一句话、最多两句,细节靠 `where` 承载,不靠堆字。evidence 用 {output_language} 书写。

```json
{"evidence": "一句话反证,没找到就写没找到反证", "where": "路径:符号,可空", "searched": "没找到时写查过什么,找到了留空"}
```

正例,需求是「必须是多 agent」而它确实是:

```json
{"evidence": "没找到反证,agents 目录确有多个独立角色协作。", "where": "", "searched": "查了 agents 目录和图编排,确为多 agent"}
```

正例,需求是「有完整的 eval 流程」而源码里没有:

```json
{"evidence": "全库没有评测脚本,拆解也没提,该能力不存在。", "where": "", "searched": "grep eval/benchmark/metric,glob **/eval*.py,均无命中"}
```

反例(作废):evidence 写成一整段分点论述;`where` 填了源码里不存在的路径或符号。
