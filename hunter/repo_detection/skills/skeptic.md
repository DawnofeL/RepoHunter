# 任务

上面 system 给了这个仓库的资料和一份架构拆解。文末是一条需求,材料区可能还附了为这条需求从源码里抠出的相关片段。

基于这些材料,为「这个仓库不满足该需求」找反证,或指出拆解说法的证据缺口。不用工具,只依据给你的拆解和源码片段判断。

# 反证长什么样

逐个类型排查,任一命中就是反证:

- 空壳实现:锚点指的地方在片段里只有几行样板或 TODO,没有实质逻辑。
- 只有示例没有实现:能力只出现在 example/demo/docs 里,主代码里不存在。
- 依赖声明了但没用:拆解提到某库,但片段和拆解里都看不到实际调用。
- 数字冲突:体积或 star 数与需求直接矛盾(如需求要轻量,体积几百 MB)。
- 拆解与源码对不上:拆解宣称的能力,对照抠出的片段明显夸大或不存在。
- 定位不符(只对问项目属于某类/某领域的定性需求):README、description、topics、拆解的定位指向的是别的类别,或定位明显夸大、与实际能力对不上。

# 取证规则

- 拆解的「关键设计」每条带 `where`(路径:符号),锚点已被核验过真实存在。核实拆解的说法是否属实、有没有夸大。
- 材料区附的源码片段(如果有)是为这条需求专门抠出来的,拿它对照拆解的说法找缺口。
- 拆解可能有错漏,它的说法不能直接当真。
- `where` 填「路径:符号」,符号是类名或函数名,多个逗号隔开。它会被程序对源码逐个核验,核不上作废,严禁编造。只填拆解或源码片段里真实出现过的路径和符号。
- 找不到反证就如实写:`evidence` 写没找到反证,`searched` 写看了什么。严禁为反而反硬凑。
- 需求问项目整体定位(定性类)的,反证是 README、description、topics 或拆解的定位跟需求不符、或定位夸大与实际对不上,以它们的原话为据,`where` 留空;定位一致、没夸大就是没有反证,别硬挑。这类不用去源码找锚点。但问项目里「有没有某个具体功能实现」的不算定性,仍按上面规则核实。
- 需求关于体量的(如「中小型」「轻量」)以体积数字为准,关于热度的(如「star 多」)以 star 数为准,数字与需求冲突就是反证,`where` 留空。
- 需求若揉了多个意思(如「适合写进简历的中小型项目」含「适合简历」和「中小型」),逐个意思找反证:任一意思有反证,整条就算有反证。

# 输出

最后只输出一个 JSON,不要别的话。evidence 一句话、最多两句,细节靠 `where` 承载,不靠堆字。evidence 用 {output_language} 书写。

```json
{"evidence": "一句话反证,没找到就写没找到反证", "where": "路径:符号,可空", "searched": "没找到时写看过什么,找到了留空"}
```

正例,需求是「必须是多 agent」而它确实是:

```json
{"evidence": "没找到反证,agents 目录确有多个独立角色协作。", "where": "", "searched": "看了拆解的关键设计和附上的片段,确为多 agent"}
```

正例,需求是「有完整的 eval 流程」而材料里没有:

```json
{"evidence": "拆解和片段里都没有评测脚本,该能力不存在。", "where": "", "searched": "看了拆解和附上的片段,无 eval/benchmark/metric 相关"}
```

反例(作废):evidence 写成一整段分点论述;`where` 填了源码里不存在的路径或符号。
