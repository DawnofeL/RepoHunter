# 任务

给你一条需求,以及正反两方各自读源码后针对这条需求给出的论据。只依据下面的材料,裁决这个仓库满不满足这条需求,满足为 hit,不满足为 miss。

- 需求:{keypoint}
- 仓库 star 数:{stars}
- 仓库体积:约 {size} MB
- 正方论据:{advocate_case}
- 反方论据:{skeptic_case}

# 裁决规则

判 hit 的依据是有正面事实证明这条需求成立,正面事实缺席就判 miss,不管正方说得多好听。什么算「事实」,看这条需求在问什么:

- 需求问「这项目是什么、属于哪类、什么领域、核心范式是什么」(定性类),那 README、description、topics 和拆解的 purpose、architecture 里明确且一致的定位就是事实,不需要 `where`。项目的自我定位通常可信,据此判即可,别卡着要源码锚点。
- 需求问「项目里有没有某个具体功能、实现、机制」(实现类),那必须有带 `where` 的源码事实。带 `where` 的已被程序核验过、真实存在,是事实;只说 README 提到、却拿不出核验锚点的,是说法不是事实,不能单凭它判 hit。README 最容易在具体功能上夸大,这类一律要源码坐实。
- 需求关于体量的(如「中小型」「轻量」)以体积数字为准,关于热度的(如「star 多」)以 star 数为准。

判断闸口就一条:需求问的是「这项目是什么」就认定位、不要 `where`,问的是「里面有没有某实现」就要源码 `where`。两头都别过界,既别拿定性需求卡 `where`,也别凭 README 一句话就给具体功能判 hit。

按两方的关系分三种情况判:

- 两方结论一致,或反方没给出反证:按正面事实判,有就 hit,没有就 miss。
- 两方各执一词、事实冲突:看谁的事实更直接命中需求的本义。比如需求是「项目包含数据集」,正方举证「已提供数据的外部下载链接且核实链接有效」,反方说「本地没有数据文件所以不满足」,那要结合需求本义判:「包含数据集」宽松、可 hit,「包含可供本地直接使用的数据集」则反方对。结合 keypoint 的确切要求裁。
- 需求只被部分满足:看满足的那部分够不够称得上需求成立。够就 hit,只是沾边、离需求本义还差得远就 miss。

只依据上面的材料,材料里没有的严禁脑补瞎编。

# 输出

只输出一个 JSON,不要别的话。`status` 是 hit 或 miss。`evidence` 写最终判断理由:冲突时必须点明采信哪方、另一方的事实为什么不推翻这个结论;一致时说清凭哪条正面事实判。evidence 用 {output_language} 书写。

实现类判 hit 的例子(靠核验过的源码锚点):

```json
{"status": "hit", "evidence": "采信正方。正方核验过 data_example 目录有现成示例训练数据(instruction 加 answer),需求要的「有提供训练数据」已被满足;反方说的主数据集要从 Google Drive 下载是另一回事,不推翻仓库内已有现成数据这个事实。"}
```

定性类判 hit 的例子(问项目属于什么,靠一致的定位判,无 `where`):

```json
{"status": "hit", "evidence": "采信正方。README 快速上手全是命令行调用、topics 带 cli、拆解 purpose 也把它定位成命令行工具,与需求「是一个命令行工具」的归类相符;这类问项目是什么的定性需求,项目自我定位一致就是事实,不需要源码锚点。反方没拿出定位不符的反证。"}
```

miss 的例子:

```json
{"status": "miss", "evidence": "采信反方。反方核验过 eval 目录只有一个空 __init__.py,没有可跑的评测代码;正方只说 README 提到评测但拿不出核验过的锚点,是说法不是事实,不足以判 hit。"}
```
