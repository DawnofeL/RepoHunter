# 任务

给你一条需求,以及正反两方各自读源码后针对这条需求给出的论据。只依据下面的材料,裁决这个仓库满不满足这条需求,满足为 hit,不满足为 miss。

- 需求:{keypoint}
- 仓库 star 数:{stars}
- 仓库体积:约 {size} MB
- 正方论据:{advocate_case}
- 反方论据:{skeptic_case}

# 裁决规则

判 hit 的唯一依据是有正面事实证明这条需求成立。正面事实缺席就判 miss,不管正方说得多好听。

论据里带 `where` 的已被程序对源码核验过,是事实;不带 `where` 的只是说法,分量比事实轻,不能单凭说法判 hit。

按两方的关系分三种情况判:

- 两方结论一致,或反方没给出反证:直接按正面事实判,有事实证明成立就 hit,没有就 miss。
- 两方各执一词、事实冲突:看谁的事实更直接命中需求的本义。比如当 keypoints 是包「项目包含数据集」，正方论据判「项目已提数据外部下载链接：xxxxx(链接)」，反方却判「由于里面没有数据文件只给了外部链接所以不满足」,你核实过发现正方给定数据链接确实有效，那就判 hit。如果 keypoint 是「项目包含可供下载的数据集」，那这个时候反方就是对的。总而言之，你需要结合 keypoint 要求来对正反方给出最终判决。
- 需求只被部分满足:看满足的那部分够不够称得上需求成立。够就 hit,只是沾边、离需求本义还差得远就 miss。

需求关于体量的(如「中小型」「轻量」)以体积数字为准,关于热度的(如「star 多」)以 star 数为准。

只依据上面的材料,材料里没有的严禁脑补瞎编。

# 输出

只输出一个 JSON,不要别的话。`status` 是 hit 或 miss。`evidence` 写最终判断理由:冲突时必须点明采信哪方、另一方的事实为什么不推翻这个结论;一致时说清凭哪条正面事实判。evidence 用 {output_language} 书写。

hit 的例子:

```json
{"status": "hit", "evidence": "采信正方。正方核验过 data_example 目录有现成示例训练数据(instruction 加 answer),需求要的「有提供训练数据」已被满足;反方说的主数据集要从 Google Drive 下载是另一回事,不推翻仓库内已有现成数据这个事实。"}
```

miss 的例子:

```json
{"status": "miss", "evidence": "采信反方。反方核验过 eval 目录只有一个空 __init__.py,没有可跑的评测代码;正方只说 README 提到评测但拿不出核验过的锚点,是说法不是事实,不足以判 hit。"}
```
